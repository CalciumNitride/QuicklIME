# 変換エンジン

エンジン (quicklime-engine) が読みを候補にする仕組みの仕様。ラティスと Viterbi、文節の分け方と文節の候補、
入力全体の N-best と候補の並び、ファジィ入力 (打ち間違いや崩した打鍵を直した候補)、逆変換、数字の書き方と日付・時刻の候補の位置、
LLM の並べ替えと生成、評価セットを扱う。

- 要求と応答の形式は [docs/protocol.md](../protocol.md)。本書はプロトコルを重複して書かず、候補の作り方と WHY を書く
- 候補を TSF 層でどう選ばせるか (変換キーの候補選択・文節 UI・後置再変換・数字の書き方の規則) は
  [conversion.md](conversion.md)、候補バーの SUGGEST の並び・予測・打鍵のファジィ照合は [suggest.md](suggest.md)
- 学習の割引の式・文節を辞書の語に分ける規則・学習の記録は学習の側
  ([learning.md](learning.md))。本書は割引がどこに効くかだけを書く
- 辞書の種類と中身・UT 辞書・単漢字辞書と記号辞書・ユーザ辞書とインポート辞書・辞書ごとの語のコストは辞書の側
  ([dictionary.md](dictionary.md))
- 英字混じりの読みの変換と英単語の大文字小文字の補正 (正しい表記の出どころと TSF 層での使い方) はモードレス入力の側
  ([modeless.md](modeless.md)「英字混じりの読みの変換」「大文字小文字の補正」)
- LLM の子プロセスの起動・監視・配布は実行と配布の側 ([runtime.md](runtime.md)「LLM の子プロセス」「LLM のモデルの取得」)。
  エンジンと quicklime-llm の間の行の形式は [docs/protocol.md](../protocol.md) の「エンジン - quicklime-llm 間」
- 実装は engine/src/convert.rs (ラティス・Viterbi・文節・N-best・補正の語)、engine/src/typo.rs (補正した読み)、
  engine/src/reverse.rs (逆変換)、engine/src/number.rs (数字の書き方)、engine/src/datetime.rs (日付・時刻)、
  engine/src/llm.rs (並べ替えと生成の規則・LLM ワーカー)、llm/src/lib.rs (quicklime-llm の SCORE・GENERATE)、
  engine/src/main.rs (要求の受付)

## ラティスと Viterbi

変換は、読みの各位置から始まる語を並べたラティスで、コストの最も小さい経路を Viterbi で求める。

### ラティスの語

| 語 | 単語コスト |
|---|---|
| システム辞書 (Mozc 辞書と UT 辞書) の語 | 辞書のコスト |
| ユーザ辞書の名詞系の語 (学習した複合語を含む) とインポート辞書の語 | 辞書ごとの定数 ([dictionary.md](dictionary.md)「語のコスト」) |
| 辞書の語に分けられなかった句の学習 (名詞の 1 語) | `UNKNOWN_WORD_COST` (12000) − 句の学習の割引 |
| 未知語 (読みの 1 文字をそのまま表記にした名詞) | `UNKNOWN_WORD_COST` (12000) |
| 英字の連続 (英単語) を 1 語にしたもの | `ASCII_WORD_COST` (5000) |
| 英字の連続を正しい大文字小文字の表記にしたもの | `ASCII_WORD_COST` − `ASCII_FORM_BONUS` (100) |

- システム辞書とインポート辞書の語は、位置ごとに共通接頭辞検索で `MAX_READING_CHARS` (16) 文字まで引く。
  ユーザ辞書の名詞系の語 (学習した複合語を含む) は読みの長さによらず載る ([dictionary.md](dictionary.md)「語のコスト」)
- 未知語はどんな読みでも経路が成り立つための保険で、辞書の語の経路が常に勝つように高くする
- 英字の連続の途中で始まる語・終わる語は作らない (英単語を途中で割らない)。英字の連続の先頭では未知語の代わりに
  連続全体を 1 語にする
- 学習した句の語の条件 (表記に数字を含む句・読み全体の句は載せない) は学習の側
  ([learning.md](learning.md)「辞書の語に分けられない句」)

### コスト

経路のコストは、語ごとの単語コストと連接コスト (Mozc の連接行列) と文節境界ペナルティの和に、最後の語から
文末への連接コストを足したもの。

- 自立語 (付属語でない語) の単語コストからは、その (読み, 表記) の語の学習の割引を引く。付属語には引かない
- 付属語は、左の品詞 ID が助詞・助動詞・接尾語 (id.def の 2 列目が「接尾」。「名詞,接尾可能」は含まない) の語

### 文節境界ペナルティ

- 自立語ごとに `SEGMENT_PENALTY` (1000) を足す。辞書にはコストの低い短いかなの語が多く、素のコストでは
  細切れの経路 (「き+き+無+れ」) が複合語 (聞き慣れ) より安くなるため。値は実辞書の回帰コーパスで決めた
  (「ききなれない」は自立語 1 語の差で約 800 が要る)
- 付属語は前の文節に付くので足さない。ただし前文脈が無いとき (文頭の文脈 ID が 0) の、文頭の直後の付属語には足す。
  付く文節が無いのにペナルティを免れて同じ読みの自立語より安くなり、「方は → 法は」「位置が → 市が」
  「無いので → ないので」のように入力の先頭が接尾語や助動詞になるため。前文脈があるときは、直前に確定した語に
  付く付属語 (「食べ」の後の「ます」) が正しいので足さない
- 予測の語の点数 (1 語だけの経路のコスト。[suggest.md](suggest.md)「点数」) と、確定した文節を辞書の語に分ける
  経路 (`split_path`) は、この文頭の例外を持たない

### 学習した文節境界

文節を伸縮して確定した文節の読み (LEARNSEG。2 文字以上) を、文節境界ペナルティの増減に使う。

- 読みの中に学習した文節の読みがあれば、その始まりと終わりの位置から始まる自立語のペナルティを
  `BOUNDARY_BONUS` (500) 減らし、その内部の位置から始まる自立語のペナルティを 500 増やす。重なったときは減らす側を優先する
- 始まりの位置で減らすだけでは、「きょうは|いいてんき」を学習しても「きょうはいい|てんき」のような、学習した文節を
  またぐ区切りを防げないため、内部にも足す
- 増減を `SEGMENT_PENALTY` より小さくするのは、辞書・連接のコストを覆すほど強くせず、学習した区切りと紛らわしい
  別の文が学習の側へ引きずられるのを避けるため
- 文節長を固定した変換 (下記) には当てない (指定された区切りを動かさないため)

### 前文脈

前文脈 (直前に確定した文節の読みと表記) から、文頭の文脈 ID (直前の語の右の品詞 ID) を復元し、文頭から最初の語への
連接コストに使う (確定をまたいでも「を」の後に名詞が出やすい)。

1. 前文脈の読みを学習を当てずに変換し、経路の表記の連結が前文脈の表記と同じなら、経路の最後の語の右の品詞 ID
2. 違えば、読みの末尾を長い順に辞書 (システム辞書・ユーザ辞書の名詞系・インポート辞書) で引き、表記が前文脈の
   表記の末尾と一致する語のうちコストの最も小さい語の右の品詞 ID (文節の末尾は助詞・助動詞・活用語尾が多く、これでほぼ拾える)
3. どちらでも引けなければ 0 (前文脈なしと同じ)

- 前文脈の読み・表記は末尾 64 文字に切り詰めて使う (長い前文脈で復元の計算が膨らまないため)
- 前文脈の文脈の句の学習は変換の経路には効かない (予測と後続語の予測だけに使う。[learning.md](learning.md)「学習の効く所」)

## 文節の分け方

経路の語を文節にまとめる。CONVSEG・CONVCTX の文節、CONVNBEST の候補の文節、補正の候補の文節、生成した候補の
文節に同じ規則を使う。

1. 連続する数字の語 (読みが数字と区切り記号だけで、末尾が数字) を 1 語にまとめる。辞書の数字は 1 桁ずつなので、
   まとめないと「12」が桁ごとの文節に割れる
   - 数字に挟まれた区切り記号 (`.` `,` `/` `:` `-` と、その全角形、記号キーで run に入るかな形の 。、・ー) も
     同じ語に取り込み、表記を記号本来の形にする (直前の数字が半角なら半角、全角なら全角)。数字に挟まれた「。」は
     句点ではなく小数点なので `0.12` と出す
   - 後ろに数字が続かない区切り記号 (「1、みかん」の読点) は取り込まない
   - 読みは run の文字の位置と対応するので変えず、表記だけを直す
2. 付属語を前の自立語にまとめる。読みの先頭の付属語は単独の文節にする

## 文節の候補 (CONVSEG・CONVCTX)

文節ごとの候補は次の順に積む。表記が同じ候補は先勝ちで除く。

| 順 | 候補 |
|---|---|
| 1 | 経路上の表記 |
| 2 | 文節の読みの句の学習の表記 (割引の大きい順) |
| 3 | ユーザ辞書の短縮よみ (読みが文節の読みに完全一致するもの) |
| 4 | 文節の読み全体に完全一致する辞書の語 (システム辞書・ユーザ辞書の名詞系・インポート辞書をコスト順に。表記が読みと同じ語は除く。システム辞書の人名は下記のとおり数を抑える) |
| 5 | 先頭の語を、その読みに完全一致する辞書の語に入れ替えた候補 (「きょうは」に「京は」) |
| 6 | 数字で始まる文節で、数字に続く部分 (助数詞など) を入れ替えた候補 (「10時」と「10次」) |
| 7 | 数字の書き方の候補 (下記「数字の書き方の候補の位置」) |
| 8 | 単漢字 |
| 9 | 記号 |
| 10 | カタカナ、ひらがな |

- 4〜6 は、1〜3 を含めた候補が `MAX_DICT_CANDIDATES` (40) 件になるまで積む。かなの同音異義語は多い
  (「きょう」は約 50 語) ため大きめにする
- 4〜6 に使う読みに完全一致する辞書の語の並びでは、システム辞書 (Mozc 辞書と UT 辞書) の人名を、コストの小さい
  `MAX_NAME_CANDIDATES` (3) 件だけコストの位置に残し、残りを人名以外の語 (ユーザ辞書・インポート辞書の語を含む) の
  すべての後ろへコストの順で回す。短い読みの同音異義語では名の人名が上位を埋め、一般名詞が枠から押し出されるため
  (「せいこう」の「正孔」は、抑えないと重複と読みと同じ表記を除いて 32 番目。抑えると 14 番目)
  - 人名は、品詞 ID 表で品詞名が `名詞,固有名詞,人名,` で始まる左文脈 ID の語 ([dictionary.md](dictionary.md)
    「連接行列と品詞 ID 表」)。品詞 ID 表が無いか読めなければ人名を判定できないので、抑えない
  - 3 件には、表記が読みと同じ人名と、先に出た語と同じ表記の人名を数えない (どちらも候補にならないため)。
    回した人名と同じ表記の人名 (名と姓の両方にある表記) は、元の位置に出ないよう一緒に回す
  - ユーザ辞書・インポート辞書の人名の品詞の語は、利用者が入れた語なので抑えない
  - 1〜3 (経路上の表記・句の学習の表記・短縮よみ) には手を入れない。学習した人名は今までどおり上に出る
  - 抑えた人名も含めて人名だけを出すのは人名変換 (F3。[conversion.md](conversion.md)「ファンクションキー変換 (F3〜F10)」)
  - 採らなかった案: 枠を広げるだけにする (人名の多い読みでは一般名詞まで遠い)。人名を候補から除く (人名変換があっても、
    変換キーの候補一覧から人名を選べなくなる)。ユーザ辞書・インポート辞書の人名も抑える (利用者が自分で入れた語のため)
- 4 を 5 より先に積むのは、先頭の語が 1 文字の読み (「した」= し+た) で入れ替えの候補が枠を使い切り、求める
  同音異義語 (下) が落ちるのを防ぐため
- 6 は、数字の部分の読みが辞書に無く 4・5 が働かないため。無いと「10次」しか出ず「10時」を選べない
- 7〜9 は枠に数えない。数字の書き方は 5 通りまでで助数詞の入れ替えの候補に押し出されないため、単漢字と記号は
  数の多い読み (「ひょう」の単漢字) で通常の語が押し出されるため
- 単漢字辞書と記号辞書の中身と引き方は辞書の側 ([dictionary.md](dictionary.md)「単漢字辞書」「記号辞書」)

### 文節長を固定した変換

CONVSEG・CONVCTX に文節長を付けた変換 (文節の伸縮。[conversion.md](conversion.md)「文節 UI (`segment_ui` 1)」)。

- 文節ごとに、その文節の読みだけで Viterbi を解き、上の規則で候補を作る。語の学習の割引は当て、学習した文節境界は
  当てない
- 文頭の文脈 ID は、先頭の文節では要求の前文脈から、2 文節目からは 1 つ前の文節の (読み, 先頭の候補) から復元する
- 経路が無い文節は、読みをそのまま表記にした 1 語にする
- 文節長の合計が読みの文字数と合わない・0 の文節長があるときは ERR

### 全文一括の候補 (CONVERT)

読み全体の最良経路の表記 (読みと同じなら入れない) → 短縮よみ → 読み全体の辞書の完全一致 (候補が 41 件になるまで。
人名の抑え方は文節の候補の 4 と同じ)
→ 単漢字 → 記号 → カタカナ → ひらがな。学習は当てない。TSF 層は使わず、開発用の engine/examples/query.rs が使う。

## N-best (CONVNBEST)

入力全体を 1 単位にした候補。区切りごと違う候補 (「今日は医者に行った」と「今日歯医者に行った」) を、文節の伸縮を
せずに選べるようにする。候補バーの全体変換 (SUGGEST)・変換キーの入力全体の候補・LLM の並べ替えの対象に使う。

### N-best の探索

- 前向きの Viterbi で各語の文頭からの最小コストを求めた後、文末から後ろ向きに A* 探索し、経路をコストの小さい順に
  取り出す。前向きの最小コストは正確な値なので、見積もりの順が経路の総コストの順と一致する
- ラティス・学習の割引・連接コスト・文節境界ペナルティ・学習した文節境界・文頭の文脈 ID は 1-best と同じ
- 取り出した経路は上の「文節の分け方」で文節に分ける
- 表記の連結が同じ経路は 1 件にまとめる (先に出たものを残す)。同じ表記の語が品詞違いで複数あり、区切りや品詞
  だけが違う経路が多く出るため
- 1-best と違う文節が同じ候補は `MAX_NBEST_PER_CLASS` (4) 件までにする。末尾の 1 文節の同音異義語だけで枠が
  埋まるのを防ぐため
  - 1-best に (開始位置, 読み, 表記) の同じ文節が無い文節の (開始位置, 読み) の並びで候補を分類する
    (1-best が「今日は|医者に|行った」なら、「今日は|医者に|言った」と「今日は|医者に|いった」は同じ分類、
    「今日|歯医者に|行った」は別の分類)
  - 分類の中は (1-best に無い語の数, 経路のコスト) の小さい順に並べ直す。語は数字をまとめた後の経路の語で、
    1-best に (開始位置, 読み, 表記) の同じ語があれば「有る」とする。区切りを変えた候補のうち、1-best の語を流用した
    もの (「今日|歯医者に|行った」) を、語を総入れ替えしたもの (「共|歯医者に|行った」) より先に出すため
  - 分類どうしの並びはコスト順のまま変えない (コスト順で分類 C が i 回目に現れる位置に、並べ直した C の i 件目を置く)
- 探索は件数では打ち切らず (並べ直しのため)、次のどちらかで止めてから `MAX_NBEST` (10) 件に切る
  - 経路のコストが 1-best のコスト + `NBEST_COST_MARGIN` (5000) を超えた (未知語まじりなど質の悪い経路を出さない)
  - 取り出した部分経路の数が `MAX_NBEST_EXPANSIONS` (3000) に達した (長い入力で打鍵を止めない)
- 定数の値は llm_cases.tsv での計測 (下記「評価セット」) で決めた

### 候補の並び

次の順に並べる。表記が同じ候補は先勝ちで除く。

| 順 | 候補 | 文節 |
|---|---|---|
| 1 | 読み全体の学習表記 (読みの句の学習のうち割引の最も大きい表記) | 読み全体の 1 文節 |
| 2 | 1-best (通常の最良経路) | 経路の文節 |
| 3 | N-best の残り (コスト順) | 経路の文節 |
| 4 | 数字の書き方の候補 (下記「数字の書き方の候補の位置」) | 2 の文節 |
| 5 | 短縮よみ・読み全体の辞書の完全一致 (コスト順。システム辞書の人名は上記「文節の候補 (CONVSEG・CONVCTX)」の 4 と同じく抑える。新しく足した件数で 40 件まで) | 読み全体の 1 文節 |
| 6 | 単漢字・記号・カタカナ・ひらがな | 読み全体の 1 文節 |

- 全体変換の補正の候補 (下記「全体変換の補正」) があれば、段階 0 では 2 の前 (先頭) か直後に 1 件入る。段階 1 以上では
  1 の前に段階ごとの件数まで入る (下記「段階 1 以上の補正の候補」)
- 5・6 は、変換の候補一覧で読みそのものの別表記を選べるようにするため。候補バーでは件数の上限でほぼ出ない
- 1-best の文節の表記は経路の表記で、文節の句の学習の表記への差し替えはしない。学習は経路のコストの割引として効く

### 保護の印

候補には次の印を付ける。LLM の並べ替えと生成、補正の候補の位置、SUGGEST の並び ([suggest.md](suggest.md)「並べ方」)
が使う。

| 印 | 付く候補 |
|---|---|
| 保護 (`protected`) | 利用者の選んだ候補と、英字 (ASCII の英文字) を含む候補・数字の書き方の候補・補正の候補 |
| 利用者の選んだ候補 (`user_chosen`) | 読み全体の学習表記、学習で表記が変わった 1-best、ユーザ辞書 (手動登録・インポート辞書・学習した複合語) の語を含む候補、短縮よみ |
| 補正 (`typo`) | 全体変換の補正の候補 |

- 「学習で表記が変わった 1-best」は、学習の割引なしのラティスを作り直して最良経路の表記 (数字をまとめた後) と
  比べて決める。段階 0 で補正の候補があるとき、段階 1 以上で補正の語を通る経路があるときと、RERANK のときだけ求め、
  毎打鍵の SUGGEST で 2 回目の Viterbi を避ける (RERANK は非同期なので増える計算を許容する)
- 段階 0 では、保護する 1-best は補正の候補に先頭を譲らない。段階 1 以上では補正の候補を保護する 1-best よりも上に置く

## ファジィ入力

打ち間違いや崩した打鍵を直した読みで変換した候補を足し、打ち直さずに選べるようにする。打ち間違いの後始末だけでなく、
崩して速く打つための入力方法として使う。全体変換の補正 (CONVNBEST・RERANK・SUGGEST) と文節 UI の補正
(CONVSEG・CONVCTX) の 2 つがある。予測のファジィ照合は [suggest.md](suggest.md)「ファジィ照合」。

- 補正の強さは段階 (下記「段階」) で決まる。設定 `fuzzy_level` (既定 0) が標準の段階で、TSF 層は run ごとに段階を
  変えて要求に付ける ([suggest.md](suggest.md)「ファジィ入力の段階」)
- かな入力 (ローマ字を使わない入力) が無いので、かな単位の誤り (清濁・大小) は戻さない

### 段階

段階は −1〜3 の 5 つで、0 が自動の補正。SUGGEST・CONVNBEST・RERANK は要求の段階を使い、段階が付いていなければ
`fuzzy_level` を使う (形式は [docs/protocol.md](../protocol.md))。

| 段階 | 全体変換の補正 | 予測の照合 ([suggest.md](suggest.md)「ファジィ照合」) |
|---|---|---|
| −1 | 作らない | ずれを許さない (完全な前方一致) |
| 0 | 末尾 `tail_chars` (1) 文字を保護、K は下記の式、最良の 1 件、Δ の足切りと位置の規則 (下記「全体変換の補正」) | 末尾も照合する。K は下記の式 |
| 1 | 末尾も補正する (`tail_chars` 0)。Δ の足切りをやめ、補正の候補を最大 3 件、先頭から出す。K は段階 0 と同じ | 段階 0 と同じ |
| 2 | 1 に加え、K を 1 増やす。補正の候補は最大 4 件 | K を 1 増やす |
| 3 | 1 に加え、K を 2 増やす。補正の候補は最大 5 件 | K を 2 増やす |

- K は許すずれの数 (全体変換の補正では、補正の語を通る数の上限)。段階 0・1 は `min(MAX_EDITS, 打鍵の数 / KEYS_PER_EDIT)`
  で、段階 2・3 は `MAX_EDITS` で抑えた後に増分を足す (段階 2 は `min(3, n / 4) + 1`)。3 打以下でも段階 2 以上では
  許すずれがある
- 先頭のかなを補正しないこと、隣り合わないキーへの置き換えを誤りとして扱わないこと、`MIN_TYPO_CHARS`、誤りの種類ごとの
  コストは、どの段階でも同じ
- 文節 UI の補正は要求の段階を受け取らない (下記「文節 UI の補正」)
- 段階から調整値を作るのは engine/src/typo.rs の `Tuning::at_level`

### 補正した読み

打ったかなに対し、1 打の誤りを戻した読みを作る (engine/src/typo.rs)。

| 補正の元 | 使う要求 | 作り方 |
|---|---|---|
| 打鍵 | 打鍵を付けた CONVNBEST・RERANK と SUGGEST | TSF 層が送ったかな 1 字ごとの打鍵の上で誤りを戻し、標準の綴りの表に run の打鍵の綴りを足した表でかなに直す |
| かなを戻した近似 | 打鍵の無い CONVNBEST・RERANK と、CONVSEG・CONVCTX | かなを標準のローマ字 (訓令式とヘボン式、ん は `nn` と、打てるところでは `n` 1 打) に戻した綴りの上で誤りを戻し、標準の表でかなに直す |

- 戻す誤りは 4 種類 (1 打ぶん)
  - 余分な 1 打を消す
  - 抜けた 1 打を足す。足す字は、ローマ字の 1 打の抜けに多い字 (母音・`n`・`y`・`h`・`s`・`t`・`k`・`r`) と、
    前後の字の重ね
  - QWERTY で隣のキー (同じ段の左右と、上下の段の隣接するもの) に置き換える
  - 隣り合う違う 2 打を入れ替える
- かなに直らないもの・元の読みと同じものは捨てる。同じ読みになる誤りが複数あれば、コストの安いほうを残す
- 先頭のかなは変えない (打鍵の補正では、先頭のかなのかたまりの打鍵には誤りを認めない)。打ち間違いが稀なうえ、
  誤補正の元になるため
- 読みの末尾の `tail_chars` (1) 文字は変えない (末尾の字を消す・変える補正と、末尾に字を足す補正を作らない)。
  候補バーは 1 打ごとに引くので、打ちかけの末尾のかなを余分・誤りとして直すと、打ちかけの読みで補正が先頭に出るため。
  全体変換の補正と文節 UI の補正の両方に効く
  - 末尾は読みの末尾の字 (かなに限らない)。英字で終わる読みでは、英字の前のかなは保護しない
- 読みが `MIN_TYPO_CHARS` (3) 文字未満なら作らない。短い読みは 1 打違いの別の語が多いため
- かな (ひらがなと ー) の連続の中だけで作る。読みに英字・数字・記号があれば、その前後のかなの連続ごとに作る
- 打鍵の要素の数がかなの文字数と合わない要求は ERR。ASCII でない要素 (文書から読んだかな) は打鍵なしとして、
  標準の綴りで補う (書式は [suggest.md](suggest.md)「打鍵の受け渡し」)
- 標準の綴りの表は TSF 層の既定のローマ字テーブル (tsf/src/romaji.cpp `kDefaultTable`) と同じ内容。利用者の
  `romaji.tsv` はエンジンから見えないので、打鍵が無いときは標準の綴りでの近似になる

### 補正の語

補正した読みごとにラティスを作り直すと毎打鍵の候補バーで遅くなるので、通常のラティスに補正の語を足し、1 回の
Viterbi で求める。

- 補正した読みで、変わった所を覆う辞書の語 (システム辞書・ユーザ辞書・インポート辞書) を、打ったかなの対応する
  区間の語にする。読みは打ったかなの区間、表記は辞書の語の表記
  - 補正後の読みの区間 [s, e2) が変わった所を含む語を、打ったかなの区間 [s, e2 − (補正後の変わった所の終わり −
    打ったかなの変わった所の終わり)) に置く
  - 区間と補正した読みの組ごとに、コストの安い `typo_words` (6) 語まで。補正した読みは数が多く、1 文字の助詞などが
    同じ区間に積み重なってラティスが膨らむため。枠を区間だけで数えないのは、同じ区間を覆う別の補正の語が枠を埋めて、
    ほかの補正の語が入らなくなるため (「すきでう」の区間「でう」で、う を余分として消す補正の「で」の品詞違いのコスト 0 の
    語が、す の抜けを足す補正の「です」を押し出す)
  - 同じ補正した読みの中で同じ語 (表記・品詞) が複数の位置から当たったときと、別の補正した読みから同じ区間に同じ語が
    来たときは、コストの安いほうの 1 つにする
  - 英字の連続の途中で始まる・終わる語は作らない
- 補正の語の単語コストには、戻した誤りのコストを足す (全体変換は誤りの種類ごとのコスト、文節 UI は一律の `TYPO_COST`)
- Viterbi は「補正の語を通った数」ごとの状態で解く。通常の 1-best と N-best は補正の語を通らない状態だけから求め、
  補正の語を通る経路は通常の候補の並びに混ざらない
- 補正の語の単語コストには語の学習の割引を当てない。補正の語を通る経路のほかの語の割引と、学習した文節境界は効く
- Δ = (通常の最良経路のコスト − 補正の最良経路のコスト) / 打ったかなの文字数。大きいほど補正のほうがよい

### 全体変換の補正

CONVNBEST・RERANK・SUGGEST の全体変換の補正。変換キーの候補一覧・LLM の並べ替え・候補バーで同じ補正の候補になる
よう、どれも同じ打鍵を受け取って同じ補正を使う。

- 補正の語のコストは誤りの種類ごと (隣のキー 3000・余分 3500・抜け 3500・入れ替え 3000。[suggest.md](suggest.md)
  「ずれのモデル」と同じ値)
- 状態は補正の語を 0〜K 個通った数で、K は許すずれの数 `min(MAX_EDITS, 打鍵の数 / KEYS_PER_EDIT)` (3 と、打鍵の数
  (未完成のローマ字を含む) を 4 で割った値の小さいほう)。打鍵が無ければ、標準の綴りで補った打鍵の数で決める。
  K が 0 なら補正しない
- 段階 −1 では作らない。以下の件数・Δ・位置の規則は段階 0 のもので、段階 1 以上は下記「段階 1 以上の補正の候補」
- 補正の候補は、1〜K 個通った状態のうち最良の経路の 1 件。文節は「文節の分け方」で区切り、文節の読みは打ったかなの区間
- Δ ≥ `TYPO_SHOW` (−50) のときだけ足す
- 位置: Δ ≥ `TYPO_TOP` (0) で、読み全体の学習表記が無く、1-best が保護 (上記「保護の印」) の対象でないときは先頭に
  置き、元の 1-best は 2 番目になる。それ以外は 1-best の直後
- 表記がほかの候補と同じなら足さない (先にある候補が残り、補正の印は付かない)
- 補正の候補は保護する (LLM の並べ替えで位置を動かさない)
- CONVNBEST・RERANK の `kinds` が無い要求にも補正の候補は入るが、補正の印は付かない (形式は [docs/protocol.md](../protocol.md))

### 段階 1 以上の補正の候補

利用者が段階を上げたときは、補正を優先して複数の候補を出す。

- 補正の語を 1〜K 個通る経路を、コストの安い順に段階ごとの件数 (3・4・5) まで取る。表記が同じ経路は安いほうの 1 件にする
  - 探索は N-best と同じく文末から後ろ向きの A* で、状態 (補正の語を通った数) ごとの前向きの最小コストを見積もりにする。
    補正の語をさかのぼるたびに状態を 1 つ戻す。取り出した部分経路の数が `MAX_NBEST_EXPANSIONS` に達したら止める
  - 文節は「文節の分け方」で区切り、文節の読みは打ったかなの区間
- 表記が補正なしの候補 (読み全体の学習表記・N-best・数字の書き方・辞書の完全一致・カタカナ・ひらがななど、並びのどれか) と
  同じ経路は出さず、件数にも数えない。補正の印が付いて学習されなくなるのを避けるため
- 並びの先頭から置き、読み全体の学習表記・保護する 1-best よりも上にする (利用者が明示的に強めたため)。その後ろは、補正の
  候補を除いた段階 0 の並び
- Δ の足切りと位置の規則は使わない。`NBEST_COST_MARGIN` も当てない
- 補正の候補が無ければ、段階 0 で補正の候補が無いときと同じ並び
- 補正の候補は保護する (LLM の並べ替えで位置を動かさない)

### 文節 UI の補正

`kinds` を付けた、文節長の指定が無い CONVSEG・CONVCTX の補正。打ち間違えた語が文節をまたいで割れる
(「よろしくおねぎあします」→ よろしく / 尾根 / ギア / します) ので、入力全体の補正の最良経路に沿って文節を区切る。

- 要求の段階を受け取らず、設定 `fuzzy_level` だけを見る。−1 なら作らず、0 以上なら以下の規則 (段階 1〜3 の違いは出ない)。
  TSF 層で run の段階を −1 にしても、文節 UI の変換には効かない
- 補正の元はかなを戻した近似、補正の語は経路に 1 つだけ (状態は 2 つ)、補正の語のコストは誤りの種類によらず
  `TYPO_COST` (4000)。Δ は `TYPO_COST` を含めて求め、しきい値 `TYPO_SHOW` (−50)・`TYPO_TOP` (0) は全体変換と同じ値を
  別の定数として持つ
- Δ ≥ `TYPO_SHOW` のときは、文節を補正の最良経路から区切る (文節の読みは打ったかなの区間)。それ以外は通常の
  最良経路から区切り、結果は補正なしと同じになる
  - Δ < `TYPO_TOP` (補正を先頭にしない) ときも補正の経路の区切りに従う。通常の経路の区切りでは、文節の範囲が補正の語と
    ずれて補正の表記を置ける文節が無いため
- 補正の語を含む文節 (補正の文節。1 つだけ) の候補は、その区間の読みだけで解いた文節長固定の変換と同じ候補に、補正の
  表記 (補正の経路のその文節の表記) を 1 件足したもの。文頭の文脈 ID は 1 つ前の文節 (先頭の文節なら要求の前文脈) から
  復元する。通常の候補に同じ表記があれば足さない (補正の印も付けない)
- 補正の表記の位置: Δ ≥ `TYPO_TOP` で、読み全体の学習表記が無く、1-best が保護 (学習で表記が変わったかも求める) の
  対象でなければ先頭、それ以外は 2 番目
- 文節長を指定した変換には補正を入れない (指定された区切りを動かせず、短い読みでのしきい値も計測していないため)
- `kinds` が無ければ補正しない。CONVNBEST と違い補正で区切りまで変わるので、印を読めない要求には補正の結果を返さない
- 打鍵による補正にしないのは、CONVSEG・CONVCTX が打鍵を受け取らないため (要求の形式は [docs/protocol.md](../protocol.md))

### 値の決め方

- `TYPO_COST` 4000・`TYPO_SHOW` −50・`TYPO_TOP` 0 は、打ち間違いの無い文 144 件 (llm_cases.tsv と typo_cases.tsv) と、
  その読みに 1 打の誤りを機械的に入れた 561 件で決めた (engine/examples/typo_eval.rs)。基準は、打ち間違いの無い文で
  補正の候補が先頭にも 2 番目にも出ないこと。この値で、打ち間違いの無い文の Δ の最大は −69 で、先頭にする下限から
  69 離れている。誤りのある文で正しい文が先頭に出たのは 52% (余分 86%・抜け 19%・隣のキー 54%・入れ替え 49%)
- `TYPO_SHOW` を `TYPO_TOP` より下げるのは、先頭にするほどではない補正を 2 番目に出すため
- 全体変換の補正を誤りの種類ごとのコストにしても `TYPO_SHOW`・`TYPO_TOP` は同じ値にした。評価
  (engine/examples/fuzzy_eval.rs) で `TYPO_SHOW` を下げると、崩していない入力で補正の候補が上位に出る件数が増えた
- 補正ありの 1 回の時間は、`convert_nbest` で中央値 1.89 ms・最大 10.61 ms、文節 UI の `convert_segments` で
  中央値 1.23 ms・最大 6.78 ms (705 読み、パイプの往復を含まない)
- 計測の条件と表は [typo-conversion.md](../archive/typo-conversion.md) と
  [typo-segment-ui.md](../archive/typo-segment-ui.md) の「計測の結果」
- 末尾の保護の `tail_chars` 1 は、打ちかけの読み (打ち間違いの無い文を 1 打ずつ打った途中の状態で、確定済みのかなが
  3 文字以上の 1984 件) で決めた (fuzzy_eval)。補正の候補かずれのある予測が候補バーの先頭に出たのは、保護なしで 10%、
  1 文字の保護で 2%。打ち終えた入力の末尾の打ち間違いが直らない損は、崩し 1 (崩した入力で正解が先頭) で 3 ポイント。
  末尾の打ち間違いは打った直後に入力パネルで見え、自分で直しやすい。2 文字の保護は先頭に出る件数をさらに減らすが、
  損が倍になる。計測の条件と表は [typo-tail.md](../archive/typo-tail.md)
- 補正の語の枠 `typo_words` 6 は、区間と補正した読みの組ごとの枠で 3・4・6 を比べて決めた (fuzzy_eval、`--config words=N`。
  崩した打ち終えた入力 434 件と打鍵ごとの SUGGEST 7176 回)。崩した入力で正解が 1 位・3 位以内・9 位以内の割合は、
  段階 0 で 3 が 27%・28%・28%、4 が 28%・29%・29%、6 が 29%・30%・31%、段階 1 で 3 が 33%・40%・41%、6 が 35%・42%・44%。
  打鍵ごとの SUGGEST の 1 回の時間の中央値・p95 は 3 つで大きく変わらない (段階 0 で 4.3〜4.8 ms・12〜15 ms)。
  打ちかけの入力で補正の候補かずれのある予測が先頭に出るのは、段階 0 で 3 つとも 1984 件中 50 件 (3%)
- 段階ごとの件数 (3・4・5) と許すずれの増分 (+1・+2) の計測 (同じ条件、`--config level=N`、枠 6)。崩した入力で正解が
  1 位・3 位以内・9 位以内の割合は、段階 1 で 35%・42%・44%、段階 2 で 35%・42%・45%、段階 3 で 35%・42%・46%。
  打鍵ごとの SUGGEST の 1 回の時間の中央値・p95 は、段階 0 が 4.8 ms・15 ms、段階 1 が 4.9 ms・14 ms、段階 2 が
  7.5 ms・23 ms、段階 3 が 10.0 ms・36 ms

### 採らなかった案

- 補正した読みごとに読み全体のラティスを作り直す。毎打鍵の候補バーで遅くなる
- 文節 UI で、文節の読みだけで補正を探す (文節ごとの補正)。打ち間違えた語が文節をまたいで割れるので直せない
- よくある誤読 (げっきょく → 月極) の対応表。1 打の誤りとは別の仕組みになる
- 通常の最良経路の 1 文字あたりのコストで補正の判定を足切りする。打ち間違いの無い文を途中で切った読みのコストが、
  打ち間違いのある文のコストと重なる (typo_eval)
- 候補バー (SUGGEST) だけに末尾の保護を当て、変換キーでは末尾も直す。候補バーと変換キーの候補一覧で補正の候補が
  食い違う
- 補正の語の枠を表記の数で数える (品詞違いの同じ表記を 1 つと数える)。コストの安い別の語が多い区間では、また押し出される
- 段階 3 で先頭のかなも補正する・隣り合わないキーへの置き換えを扱う。先頭のかなの打ち間違いも、隣り合わないキーへの
  打ち間違いもまず起きず、誤補正の元になる
- 段階を上げたときの補正の候補を 1-best の直後から並べる。利用者が明示的に強めたので、補正を優先して先頭に置く
- 文節 UI にも段階を効かせる。CONVSEG・CONVCTX は打鍵を受け取らず、補正の語も経路に 1 つだけの別の仕組みで、作業が
  大きく増える
- 設定 `typo_correction` (0/1) の値の範囲を広げて段階にする。`typo_correction 0` と書いている人の設定が段階 0
  (自動の補正あり) と読まれ、意味が逆になる

## 逆変換 (REVERSE)

表記を語ごとの (読み, 表記) の列にする (engine/src/reverse.rs)。漢字を含む選択の再変換
([conversion.md](conversion.md)「漢字を含む選択の再変換」) と、文節の連なりの統計の生成
([suggest.md](suggest.md)「文節への分け方」) が使う。結果は最良の 1 通りだけ。

- 表記の文字の格子に表記で引いた語を並べ、変換と同じ単語コスト (語の学習の割引を含む)・連接コスト・文節境界
  ペナルティで最小コストの経路を選ぶ。前文脈は無いので、先頭の付属語にもペナルティを足す
- 結果の単位は経路の語で、文節にまとめない (前文脈と、表記が変わった文節の判定にしか使わないため)
- 表記に使える文字は、ひらがな・カタカナ・ー・漢字 (CJK 統合漢字・拡張・互換漢字)・々・〇・〆・数字 (半角・全角)。
  ほかの文字を含む・格子が文末まで繋がらない・読みの合計が `MAX_READING_LEN` (127) 文字を超えるときは失敗

### 格子の語

| 表記 | 語の引き方 |
|---|---|
| 漢字・々 を含む表記 | 逆引きの索引 (下記) とユーザ辞書で、表記の前方一致の語を引く。表記に数字を含む語は使わない |
| かなだけの表記 | 読みは表記そのもの (カタカナはひらがなに直す) に決まるので、読みの辞書をその読みで引き、表記が一致する語を使う |
| 数字の並び | 読みが数字そのもの (半角・全角は元のまま) の 1 語。品詞 ID とコストは 1 桁ずつの数字の語を連ねたもの (変換で数字の語をまとめたときと同じ) |
| かな 1 文字 | 読みがその文字 (ひらがな。ヶ は け) の未知語。単語コスト `UNKNOWN_WORD_COST` (12000) |
| 漢字 1 文字 | 単漢字辞書を逆に引いた読みの語。単語コスト 12000 (辞書の語で読めない漢字に使われるようにする) |

- 表記に数字を含む辞書の語 (3日 → みっか) を使わないのは、読みから数字が消え、再変換の候補が打った数字から作られなくなるため
- 引く表記の長さは `MAX_READING_CHARS` (16) 文字まで

### 数字の直後の助数詞の読み

辞書には助数詞の読みが複数あり、数字の後では使わない読みのほうが安いことがある (日 は ひ 1734・にち 1826、
人乗り は ひとのり・にんのり。品詞と連接コストが同じなので語のコストで決まる)。数字の後の読みの表
(`COUNTER_READINGS`) を持ち、次をすべて満たす語を格子から外す。

- 数字の直後から始まる
- 品詞が `名詞,接尾,助数詞`
- 表記が表の見出しで始まる (複数の見出しが当たるときは最長のもの)
- 読みが表の読みのどれでも始まらない。濁点・半濁点を外して比べる (ぷん・ぶん は ふん で受ける)
- 学習にある組でない

| 見出し | 数字の後の読み |
|---|---|
| 日 | にち |
| 人 | にん |
| 時・次・字 | じ |
| 年・歳・名・問・巻 | ねん・さい・めい・もん・かん |
| 戦・銭 | せん |
| 話・種 | わ・しゅ |
| 色・食 | しょく |
| 軒・店 | けん・てん |
| 戸・個 | こ |
| 床・勝・章 | しょう |
| 球・泊・畳・元・円・合 | きゅう・はく・じょう・げん・えん・ごう |
| 世・体・位・通・連・重・品・棟 | せい・たい・い・つう・れん・じゅう・ひん・とう |
| 行 | ぎょう・こう |
| 分 | ふん |
| か月・カ月・ヶ月・ヵ月・ケ月 | かげつ |

- 表に入れないもの: 数字の後でどちらの読みも使う助数詞 (羽・把・割・枠・夜・石・文) と、辞書で正しく読める
  助数詞 (月 など)
- 見出しは語の先頭だけを見るので、単位の後ろの部分の読み (キロ位 → きろい) は直らない ([roadmap.md](../roadmap.md) の既知の問題)

### 学習の優先

- 学習にある (読み, 表記) の組 (語の学習の割引があるか、句の学習にある組) の語があれば、同じ位置・同じ表記で読みの違う
  語を格子から外す。その人がその表記をその読みで打ったことがあり、学習の割引だけでは辞書のコストの差
  (きょう/今日 と こんにち/今日) を覆せないため

### 逆引きの索引

- システム辞書 (Mozc 辞書と UT 辞書) の語のうち、表記に漢字・々 を含む語を、表記の前方一致で引けるようにする。
  かなだけ・英字だけの表記は読みが表記から決まるので入れない
- 持ち方: 語の辞書の中の位置を表記の順に並べた配列にし、二分探索で範囲を絞って引く。語の読みは、読みごとの語の
  開始位置の配列から求め、読みの fst を値から逆に引いて得る (読みの文字列を索引に複製しない)
- システム辞書の分は、エンジンが待ち受けを始めた後に別スレッドで作る (約 1 秒)。できるまでの REVERSE は ERR を返す
  (変換キーはアプリへ渡る)
- インポート辞書の分は同じ形の索引を読み込み時と RELOADUSER で作る。手動登録の語は件数が少ないので線形に見る

### 採らなかった案

- 逆引きの索引にすべての語 (かなだけの表記を含む) を入れる。かなの表記は読みの辞書で引けば足り、メモリが増えるだけ
- 逆引きの索引を「表記 + 読み」をキーにした fst にする。表記が先頭のキーは圧縮が効かず (約 70MB)、起動時の構築に
  約 4 秒かかった
- 語の読みを索引の中の文字列の表に持つ。検索は約 4 倍速い (1 回約 1.5µs と約 6µs) が、メモリが約 3 倍 (約 44MB) になり、
  選択 1 回の逆変換では速さの差が問題にならない
- 逆変換の読みを複数返す。選ばせる UI が要るので 1 通りにする ([conversion.md](conversion.md)「漢字を含む選択の再変換」)

## 数字の書き方の候補の位置

数字で打った数の別の書き方 (位取りの漢数字・並べた漢数字・桁区切り・万の単位まじり・全角/半角。規則は
[conversion.md](conversion.md)「数字の書き方の候補」) を、次の位置に足す (engine/src/number.rs)。

- 文節の候補 (文節長を指定しない CONVSEG・CONVCTX): 先頭の語が数字の語 (「文節の分け方」でまとめたもの) の文節で、
  数字の部分を書き方ごとに置き換え、続く部分は経路の表記のままにした候補
  (`1234えん` → `千二百三十四円`・`一二三四円`・`1,234円`・`１２３４円`)。位置は数字に続く部分を入れ替えた候補の後ろ、
  単漢字の前。書き方の順に並べる
- 入力全体の候補: N-best の後ろ (短縮よみ・辞書の完全一致の前) に、1-best の文節のうち数字の語で始まる文節をすべて同じ
  書き方にした候補を、書き方ごとに 1 件足す (`1234えんと5600えん` → `千二百三十四円と五千六百円`)。文節は 1-best の
  文節のまま表記だけを置き換える。文節の表記が学習で数字ごと変わっている (`1,234円`) ときは、数字に続く部分に経路の表記を使う
- 入力全体の候補の数字の書き方は保護する。数字の読みに対する漢数字などは LLM の尤度が高く出やすく、打ったとおりの数より
  上に並べ替えられるのを避けるため

## 日付・時刻の候補

F4 (記号・日付変換) の CONVSYM で、記号辞書の候補の後ろに、エンジンの現在の日時から作った表記を出す
(engine/src/datetime.rs)。

| 読み | 候補 |
|---|---|
| きょう・あした・あす・あさって・きのう・おととい | その日の `2026/07/15`・`2026年7月15日`・`7月15日(水)`・`令和8年7月15日` |
| ことし・らいねん・きょねん | その年の `2026年`・`令和8年` |
| いま | `14:30`・`14時30分`・`午後2時30分` |

- 和暦は平成以降 (それより前の年は和暦の候補を出さない)。元号は西暦の年で決め、1 年目は「元」と書く
- 通常の変換には混ぜない。同音異義語の多い読みでは候補の奥に埋もれるため
- 学習しない (LEARN・LEARN2・LEARNWORD で、その時点の日時の候補と同じ表記を除く)。学習すると翌日以降も古い日付が
  先頭に来るため

## LLM の並べ替え

zenz 系のかな漢字変換モデル (別プロセス quicklime-llm) で、CONVNBEST の上位の候補を尤度の順に並べ替える。統計変換
(連接コストと学習) は文脈による同音異義語の判別が弱く、手作りの候補群 (llm_cases.tsv 50 件) の 1 位の正解率は
統計の 1-best の 50% に対し LLM は 84〜88%、N-best の上位 10 件には正解が 94% 入っていた
([experiment-0b-llm-results.md](../archive/experiment-0b-llm-results.md))。

- 打鍵を止めないよう、推論は非同期に行い、結果は候補バーと変換キーの候補一覧に後から反映する (TSF 層での反映は
  [suggest.md](suggest.md)「LLM の並べ替えの結果の反映」)
- 設定 `llm` (既定 0) が 0 のとき、TSF 層は RERANK を送らず、エンジンは子プロセスを起動しない。LLM が使えない環境でも
  統計変換だけで同じように動く

### 並べ替える依頼

- RERANK は CONVNBEST と同じ候補 (同じ打鍵の補正を含む) を作って LLM に渡す。学習で表記が変わった 1-best の判定は
  補正の候補の有無によらず行う
- 読み (RERANK のかな) が `RERANK_MIN_CHARS` (9) 文字より短い依頼は並べ替えない (`llm` 0 と同じく ID 0 を返し、LLM に送らない)
  - 実ユーザの learning_stats.tsv の句から作ったセット (Vulkan + small) で、全件を並べ替えると 1 位の割合が
    84.6% → 80.9% (文脈なしの句)・91.1% → 88.8% (直前の文節を左文脈にした句) に下がり、損は短い読みに集中していた。
    9 文字以上だけを並べ替えると 85.2%・91.1% で損が消え、AJIMEE-Bench (読みの平均 28 文字) の得 (51.8% → 71.6%) は
    残る。CPU + xsmall も同じ傾向
  - 短い読みでは統計変換の 1 位が 8〜9 割当たっており、LLM の尤度の差は文脈があってもそれを崩す方に多く働く
  - 代わりに、短い読みで左文脈によって決まる同音異義語 (llm_cases.tsv。全件なら 1 位 90%、この条件で 52%) は LLM では
    直らない。これは学習に任せる
  - 計測用に、エンジンは起動時の環境変数 `QUICKLIME_RERANK_MIN_CHARS` (0 以上の整数。不正なら既定値) でこの値を上書きする
- 右の文脈は使わない ([conversion.md](conversion.md)「変換の対象」)

### モデルと尤度

| 設定 `llm_backend` | 子プロセス | モデル |
|---|---|---|
| `cpu` (既定) | quicklime-llm.exe | zenz-v3.2-xsmall (Q5_K_M) |
| `vulkan` | quicklime-llm-vulkan.exe | zenz-v3.2-small (Q5_K_M) |

- Vulkan 版が起動できないときは CPU 版と xsmall で動く ([runtime.md](runtime.md)「Vulkan 版から CPU 版への切り替え」)
- CPU のスレッド数は min(4, 論理コア数)。実験 0b で 4 と 6 の差は小さかった
- プロンプトは zenz-v3 の書式 (azooKey の ZenzPromptBuilder と同じ): 左文脈があれば U+EE02 と左文脈 (末尾 40 文字)、
  U+EE00 と読み (カタカナ)、U+EE01。半角スペースは U+3000 にし、改行は除く (zenz のトークナイザが扱えないため)
- モデルの読み込み時に、メタデータ `tokenizer.ggml.pre` を `gpt-2` に上書きする。zenz の GGUF の前処理の種類は上流の
  llama.cpp が読めず、azooKey の llama.cpp のフォークは同じものを GPT-2 と同じ正規表現で扱っているため
- 候補の尤度は、候補の全トークンと終端の `</s>` の対数確率の和。zenz が出力の終わりに出すのは `</s>` で、語彙の EOS
  (`<s>`) の確率は文の終わりを表さず、送り仮名を落とした形や語の途中で切れた候補を上げる。AJIMEE-Bench (197 件) の
  並べ替え後の 1 位は、語彙の EOS では Vulkan + small で 131 件・CPU + xsmall で 121 件、`</s>` では 141 件・124 件。
  `</s>` は読み込み時に語彙の文字列から引き、無いモデルでは語彙の EOS を使う
- 推論はプロンプトを 1 回だけ評価し、その KV キャッシュを候補の数だけ複製して全候補を 1 回の decode で評価する
  (実験 0b で最も速かった方式)。文脈の長さは 512 トークン、候補は 15 件まで。収まらない入力は ERR

### 左文脈

LLM の左文脈は「run の先頭より前」の文字列 (azooKey Desktop の行単位の文脈に合わせる)。composition 入力では読みが
文書に入るので、キャレットの前を後から読まず、run の最初の打鍵の前に読む。入力なしの対象から始めた変換の左文脈は
[conversion.md](conversion.md)「前の文脈」。

| 文書 | 左文脈 |
|---|---|
| 読める文書 | run を始めるとき、キャレットの前を最大 80 (UTF-16 単位) 読んだもの。transitory な文脈は親の文脈で読む (Mozc と同じ) |
| それ以外 | IME が文書に入れた文字列 (採用・確定した文字列、IME が入れたスペース) の末尾 40 文字の履歴 |

- run の間は読み直さない (run の間に IME は前方を書き換えない)。採用範囲を縮めた採用の後は、run を始めたときの左文脈に
  採用した文字列を足す (文書を読み直さない。azooKey Desktop と同じ)
- 履歴は、前文脈を捨てるとき (キャレット移動・フォーカス移動など) と、Enter・Ctrl+M をアプリへ渡したときに捨てる
  (IME が入れた文字列がもうキャレットの前・同じ行にあるとは限らないため)
- TSF 層は最後の改行より後ろだけを残し、タブをスペースにする。エンジンは先頭の空白を除き、末尾 40 文字
  (`LLM_CONTEXT_CHARS`) にし、半角スペースを U+3000 にする
- 左文脈はメモリ上だけで使い、debug_log・学習ファイルなどに書かない。debug_log には長さだけを書く
- 統計変換の前文脈 (直前の確定の文節) は別に送る

### 並べ替えの規則

- 並べ替えの対象は、候補の上位 `RERANK_TOP` (10) 件のうち保護しない候補 (上記「保護の印」)。保護する候補と 11 件目
  以降は位置を動かさない
- 対象の候補を尤度の高い順に、対象の候補があった位置へ詰め直す。同じ尤度は元の順を保つ
- 対象が 2 件未満なら LLM に採点させない (並べ替えの結果は元の並び)
- 英字・数字の書き方・補正の候補を保護するのは、LLM で公平に採点できないため。学習・ユーザ辞書の候補は、利用者が
  選んだ・登録した表記なので動かさない

### 依頼と結果

TSF 層にはスレッドを作らず、エンジンへの要求はどれもすぐに応答する (形式は [docs/protocol.md](../protocol.md)
「RERANK / RERANKGET」)。

- RERANK は依頼を受け付けて接続ごとに 1 から増える ID を返す。0 は並べ替えをしないこと (`llm` 0・短い読み・子プロセスが
  READY を返す前や停止中)
- 子プロセスとのやり取りは、エンジン内の専用のスレッド (LLM ワーカー) 1 本だけが行う。同じ接続のまだ始まっていない
  依頼は新しいものに置き換える (古い読みの推論をしない)
- 結果は接続ごとに最新の 1 件だけ持つ。RERANKGET は、最新の ID でなければ NONE、推論中・順番待ちなら PENDING、
  結果があれば DONE、推論に失敗していれば NONE を返す
- 1 要求の応答が 2 秒 (`LLM_TIMEOUT_MS`) を超えた依頼は NONE にする (TSF 層は統計の並びのまま)。子プロセスの異常の
  判定と再起動は [runtime.md](runtime.md)「応答待ちと異常」

### 採らなかった案

- 統計変換の 1 位と 2 位のコスト差 (読み 1 文字あたり) がしきい値以下のときだけ並べ替える。どのしきい値と読みの長さの
  組でも、9 文字以上だけを並べ替えるときの実ユーザのセットの 1 位の割合を上回らなかった

## LLM による候補の生成

並べ替えは N-best の上位 10 件の中でしか順位を直せず、そこに正解が無い件 (長い読みで 1 か所だけ語の選び方を誤った件
など) には届かない。Vulkan 版では、zenz の貪欲法で生成した表記を 1 件足す。

- 実験 0c ([experiment-0c-llm-gen-results.md](../archive/experiment-0c-llm-gen-results.md)) で、AJIMEE-Bench (197 件) の
  1 位は並べ替えだけで 141 件 (72%)、生成した候補を先頭に置くと Vulkan + small の貪欲法で 169 件 (86%)。遅延の p95 は
  並べ替えとの合計で 84 ms
- CPU + xsmall は得 31 件に対して失が 13〜15 件あり、得が小さい
- 実ユーザの句のセットでは、短い読みに生成をかけると 1 位が下がる (全件で 85.2% → 81.1%)。9 文字以上だけにすると損得は
  ほぼ無く (85.2%・91.1% のまま)、AJIMEE-Bench の得 (72% → 83%) は残る

### 生成する条件

- 子プロセスが Vulkan 版で動いている (`llm_backend` が `vulkan` でも、CPU 版に切り替えて動いている間は生成しない)
- 並べ替えをする依頼 (読みが `RERANK_MIN_CHARS` 文字以上)。生成のしきい値は並べ替えと同じ定数を使う

### 生成

- ワーカーは並べ替えの SCORE の応答の後に GENERATE を送る。対象が 2 件未満で SCORE を送らない依頼でも送る
- SCORE が ERR を返したとき (プロンプトと候補が文脈の長さに収まらない長い読みなど。子プロセスは正常) も送り、並べ替えて
  いない並びに生成した候補を入れる。生成はプロンプトに出力 1 件を足すだけで、候補を並べる SCORE より短く収まるため
- quicklime-llm は SCORE と同じプロンプトから貪欲法 (毎トークン最大の確率) で生成し、EOG トークン (`</s>` を含む) で
  止める。生成するトークン数の上限は読みの文字数 × 2 + 8。上限に達したとき・出力が UTF-8 として正しくないときは表記を
  空で返す。プロンプトと出力が文脈の長さ (512 トークン) に収まらなければ ERR
- GENERATE が ERR・空の表記・下記の後処理で捨てた出力なら、生成なしの並べ替えの結果にする (SCORE も ERR だったときは NONE)
- 応答待ちの時間の扱いは SCORE と同じ

### 後処理

- ルビを除く: 括弧 (`(` `)` `（` `）`) の中がかな (ひらがな・カタカナ・ー) だけで空でなければ括弧ごと消す。読みに
  その括弧があれば消さない
- 次の出力は捨てる
  - 空
  - 文字数が読みの文字数を超える
  - 同じ 2 文字以上の並びが 3 回以上続けて現れる (読みに同じ繰り返しがあれば判定しない)
  - 私用領域の文字 (プロンプトの区切りの U+EE00〜 を含む) を含む

### 並びへの入れ方

- 位置は、並びの先頭から見て最初の、利用者の選んだ候補でない候補の位置。すべてが利用者の選んだ候補なら末尾
- 同じ表記の候補が並びにあるとき
  - 利用者の選んだ候補なら何もしない
  - それ以外 (利用者の選んだ候補でない保護する候補を含む) なら、その候補を上の位置へ動かす (候補の数は増えない。
    動かした候補の文節と印はそのまま)
- 同じ表記が無ければ、上の位置に新しい候補として入れ、後ろの候補は 1 つずつ下がる (候補の数が 1 増える)
- 生成した候補は保護しない・補正の候補でない・利用者の選んだ候補でない
- 英字・数字の書き方・補正の候補より前に入れるのは、それらは LLM で公平に採点できないので並べ替えから外しているだけで、
  生成した候補より優先する理由が無いため。AJIMEE-Bench (誤りの無い読み) では、先頭に来たこれらの候補が外れで、生成した
  正解がその下になる件が 15 件あった

### 生成した候補の文節

学習と採用範囲の縮めに使う文節を、RERANKGET で DONE を返すときに決める。

- RERANK の依頼の前文脈と読みのラティスで、表記の連結が生成した表記と等しい経路のうち最小のコストのもの
  (表記の制約つきの Viterbi `constrained_path`) を、「文節の分け方」で区切った文節にする
- 経路が無ければ (数の書き方など、辞書の語でたどれない表記) 読み全体を 1 文節 (読み, 生成した表記) にする
- ワーカーのスレッドからは辞書を使わないので、ワーカーは生成した表記と入れた位置を結果に持たせ、RERANKGET を処理する
  スレッドが文節を決める
- 採用・確定したときの学習は、ほかの全体変換の候補と同じ

### 採らなかった案

- 生成の有効・無効の設定を足す。CPU 版では得が小さく、Vulkan 版では使わない理由が無い
- 辞書のラティスに制約した照合 (統計変換をドラフトにして LLM の予測と照合する Zenzai の方式) と、読みから外れた出力だけを
  それに代える組み合わせ。どちらも貪欲法だけより 1 位が低い。読みから外れた出力は数の書き方の正解が多く、代えると得が
  減って失は減らない

### 再生評価

実ユーザの learning_stats.tsv を入力に、実際に打った文での変換・予測と学習の効き方を測る (`learning_eval`)。
learning_stats.tsv は起動時に 1 件 1 行へ書き直されて確定の並びが残らないので、各件の最後に使った通し番号 `t` の順を
確定の順の近似として使う。書式と度合い `d` は学習の側 ([learning.md](learning.md)「使った度合いと割引」「learning_stats.tsv」)。

- 同じ件は後の行を使う (エンジンの読み込みと同じ。件のキーは `w`・`p` が (読み, 表記)、`q` が (文脈, 読み, 表記))
- 学習が空のモード: すべての `p` の行 (句の学習) の読みを CONVNBEST と同じ関数 (補正なし) で変換し、行の表記が 1 位・
  3 位以内に入る割合
- 学習ありのモード: `w`・`p`・`q` の件を `t` の順に並べ、件の数の 8 割の位置にある件の `t` 以下を前、それより大きい件を
  後ろとする。前の件を `d` と `t` のまま取り込み、後ろの `p` と `q` の件を測る
  - 同じ `t` の件は前と後ろに分けない。1 回の確定で数えた件や、古い learning_context.tsv の取り込みの件は同じ `t` を持つため
  - 後ろの件のうち `d - 1` が 0.05 (`MIN_KEEP`) 以上の件は、分け目より前にも使っていたとみなし、`d - 1` と分け目の `t` で
    前の学習にも入れる。同じ件は後の行にまとめるので、こうしないと繰り返し使った件だけが自分の学習を失い、学習が不利な
    方向に測られる
  - 変換 (`p` の行): 1 位・3 位以内の割合
  - 予測 (`p` と `q` の行): 読みを標準のローマ字にした打鍵の先頭 50% (切り上げ) で SUGGEST を引き、9 位以内に入る割合。
    `q` の行は文脈の表記を前文脈にする
  - 測る行を既出 (前の学習に入れた件か、(読み, 表記) が前の `p` か `q` の件にもある行) と初出に分けても出す
- 文節の `p` の行で同じ (読み, 表記) の `q` の件があるものは、前の文節を前文脈にして変換する。実際の入力では前に語があり、
  文頭から変換すると入力の先頭にしか起きない外れ (「方は → 法は」) を数えてしまうため。文脈の読みは同じ表記の文節の
  `p` の件から引き、引けない行は前文脈なしで変換する
- 読みに ASCII 英字を含む `p` の行は変換の測定から除く。モードレス入力の英字区間は (読み = 表記) の句として学習に入るが、
  実際の入力では変換に渡らないため。学習の取り込みと既出・初出の判定には含める
- 1 位を外した行は、正解と 1 位の自立語の違いで分類して数える (固定・分けられない・自立語が同じ・同じ区間・区切り・同音・
  その他)。外れが割引の上限の例外と前文脈のどちらで直りうるか、区切りの外れが辞書と連接のコストのどこで起きているかを見るため。
  区切りと同じ区間の内訳、1 位を読み全体の学習表記で固定した得失、学習が空のモードの行の位置ごとの割合も出す
- `--next-word` で、後ろの `q` の行の表記が後続語の予測 (NEXTWORD) の 9 位以内・1 位に入る割合を、学習と文節の連なりの
  統計のあり・なしの 4 つの組で出す
- 出力は件数と割合だけで、読み・表記は書かない。個々の行を見る `--dump-same-span`・`--dump-boundary`・`--dump-pinned` は
  実際の入力がそのまま入るので、標準出力には書かず、リポジトリの外のファイルに書く
- ファイルは読むだけで、学習はメモリ上にだけ作る。LLM の並べ替えは再生評価では測らない (`nbest_eval --llm` で測る)
- 後ろの件の `d - 1` には、分け目より後で最後の確定より前の使用も含まれうる (区別する記録が無い)。その分だけ既出の行が
  学習に有利に測られるが、後ろの区間は短いので近似として受け入れる

### 採らなかった案

- AJIMEE-Bench の TSV をリポジトリに入れる。MIT のリポジトリに CC BY-SA のデータを混ぜることになる (取得スクリプトなら
  再配布しない)
- 評価用に確定の記録を別ファイルに貯める。打った文がそのまま残る。`t` の順の近似で足りなければ改めて検討する
- `nbest_eval` に JSON を直接読ませる。エンジンの crate に JSON の依存が増える

## 設定

値の書式と設定ツールでの名前は [設定一覧](../user/settings.md)。

| 設定 | 既定 | 読む側 | 本書での働き |
|---|---|---|---|
| `fuzzy_level` | 0 | エンジン・TSF 層 | ファジィ入力の標準の段階 (−1〜3。上記「段階」)。段階の付いていない要求と文節 UI の補正の有無に使う。範囲外・数値でない値は既定値。行が無く `typo_correction 0` があれば −1 として読む |

| `llm_backend` | `cpu` | エンジン | `cpu` / `vulkan`。子プロセスとモデルを選ぶ |

- エンジンは起動時と RELOADCONFIG で設定を読む。`llm`・`llm_backend` が変わったときの子プロセスの起動・終了は
  [runtime.md](runtime.md)「起動と終了」
