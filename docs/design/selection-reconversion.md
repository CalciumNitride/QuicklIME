# 漢字を含む選択範囲の再変換 (逆変換)

## 背景と目的

run が無いときの選択範囲の再変換 (後置再変換) は、ひらがな・カタカナ・ー だけの選択に限られている
(docs/design/conversion-range.md)。漢字を含む部分を直せるのは、IME が入れた文字列の記憶と一致する
ときだけで (docs/design/adopted-reconversion.md)、ほかのアプリで入れた文字列・記憶を捨てた後の文字列・
別の IME で入れた文字列は、読みを打ち直すしかない。

表記から読みを推測する逆変換をエンジンに足し、漢字を含む任意の選択範囲を変換キー・F6〜F10 で
再変換できるようにする。

## 決定事項

### A. 対象

- run なし・選択ありで、選択がかなだけでないとき (かなだけの選択は今どおり)
- 選択の文字は、ひらがな・カタカナ (ヶ を含む)・ー・漢字・々・〇・〆・数字 (半角 `0`〜`9`・
  全角 `０`〜`９`) に限る。
  英字・記号・空白・改行を含む選択は対象外とし、今どおり変換キーをアプリへ渡す
- 選択の長さは今の後置再変換と同じく 127 文字 (`kMaxReconvertLength`) まで。逆変換した読みも
  127 文字までとし、超えたら対象外にする
- 選択の読み戻しの照合 (`MatchRunEditSession`) は今どおり行い、一致しなければ対象外
- 逆変換に失敗したら (読めない文字がある)、対象外にする
- 選択が無いときの対象 (キャレット直前の記憶・かな) は今のまま。逆変換は使わない

### B. 逆変換 (エンジン)

表記を、文節ごとの (読み, 表記) の列にする。結果は 1-best の 1 通りだけを返す。

- 表記の文字の格子に、表記で引いた語を並べ、今の変換と同じ語のコストと連接コストで Viterbi を
  かけて最小コストの経路を選ぶ
- 語の引き方:
  - 漢字・々 を含む表記: 表記をキーにした逆引きの索引 (下記) で、表記の前方一致の語を引く
  - かなだけの表記: 読みは表記そのもの (カタカナはひらがなに直す) に決まるので、今の読みの辞書を
    その読みで引き、表記が一致する語を使う。逆引きの索引には入れない
  - 数字の並び: 読みは数字そのもの (半角・全角は元のまま) の 1 語にする。今の変換の
    `merge_digit_runs` でまとめた数字の語と同じ扱い。表記に数字を含む辞書の語 (3日 → みっか など) は
    使わない。読みから数字が消え、再変換の候補が打った数字から作られなくなるため
  - 数字の直後の助数詞の読み: 辞書には助数詞の読みが複数あり、数字の後では使わない読みの方が安いことが
  ある (日 は ひ 1734・にち 1826、人乗り は ひとのり・にんのり。品詞が同じで連接コストも同じため
  語のコストで決まる)。数字の後の読みの表 (`reverse.rs` の定数) を持ち、次をすべて満たす語を格子から外す
  - 数字の並びの直後から始まる
  - 品詞が `名詞,接尾,助数詞` (id.def の 2 列目が 接尾・3 列目が 助数詞)
  - 表記が表の見出しで始まる (複数の見出しが当たるときは最長のもの)
  - 読みが表の読みのどれでも始まらない。比べるときは濁点・半濁点を外す (ぷん・ぶん は ふん で受ける)
  - 学習にある (読み, 表記) の組でない
  - 表 (見出し → 数字の後の読み):
    日 → にち、人 → にん、時・次・字 → じ、年 → ねん、歳 → さい、名 → めい、問 → もん、巻 → かん、
    戦・銭 → せん、話 → わ、種 → しゅ、色・食 → しょく、軒 → けん、店 → てん、戸・個 → こ、
    床・勝・章 → しょう、球 → きゅう、泊 → はく、畳 → じょう、元 → げん、円 → えん、合 → ごう、
    世 → せい、体 → たい、位 → い、通 → つう、連 → れん、重 → じゅう、品 → ひん、棟 → とう、
    行 → ぎょう・こう、分 → ふん、か月・カ月・ヶ月・ヵ月・ケ月 → かげつ
  - 表に入れないもの: 数字の後でどちらの読みも使う助数詞 (羽・把・割・枠・夜・石・文) と、
    今の辞書で正しく読める助数詞 (月 など)
  - 見出しは語の先頭だけを見るので、単位の後ろの部分の読み (キロ位 → きろい) は直らない
    (docs/roadmap.md の既知の問題)
- どの語にも当たらないかな 1 文字: 読みはその文字 (ひらがなに直す) の語を置く。コストは高くする
  - 辞書の語に当たらない漢字 1 文字: 単漢字辞書 (single_kanji.tsv) を逆に引いた読みの語を置く。
    コストは辞書の語より高くする
- 逆引きの索引: システム辞書 (Mozc + UT) とユーザ辞書のうち、表記に漢字・々 を含む語だけを、
  表記の前方一致で引けるようにする
  - 持ち方: 対象の語の辞書内の位置を表記の順に並べた配列にし、二分探索で範囲を絞って引く。
    語の読みは、読みの run の開始位置の配列から run を求め、読みの fst を値から逆に引いて得る
    (UT 込みで約 161 万語・約 13.5MB)
  - 構築: システム辞書の分は、エンジンが待ち受けを始めた後に別スレッドで作る (約 1 秒)。
    できるまでの REVERSE は ERR を返す (変換キーは今どおりアプリへ渡る)。ユーザ辞書の分は
    読み込み時と RELOADUSER で作る (インポート辞書は同じ索引、手動登録の語は件数が少ないので線形に見る)
- 学習: 学習にある (読み, 表記) の組は、同じ表記の別の読みより優先する
  (その人がその表記をその読みで打ったことがあるため)。学習にある組の語があれば、同じ位置・同じ表記で
  読みの違う語を格子から外す。変換と同じ学習の割引だけでは、辞書のコストの差
  (きょう/今日 と こんにち/今日 など) を覆せないため
- どの経路でも格子が繋がらない (読めない文字がある) ときは失敗を返す
- 文節: 結果の単位は Viterbi の語にする。文節にまとめない (記憶の文節と同じく、前文脈と
  学習の判定 (E) にしか使わないため)

### C. プロトコル

新しいコマンド REVERSE を足す。

```
REVERSE\t<表記>
→ OK\t<読み>\x1f<表記>\t<読み>\x1f<表記>...
→ ERR (読めない文字がある・対象外の文字がある)
```

### D. 再変換の流れ (TSF 層)

逆変換の結果を、記憶 (`AdoptedText`) から始める変換と同じ形にして、その経路を使う
(docs/design/adopted-reconversion.md の「変換キー・F6〜F10 の対象」と「確定と取消」)。

- run の読みは逆変換の読みの連結。打鍵列は読みの文字そのもの (今のかなの選択と同じ)
- 候補の先頭には元の表記を置く (変換キーを押しただけでは文書は変わらない)。
  2 回目の変換キーから次の候補へ進む
- F6〜F10 は読みに対して働く (漢字の選択に F7 でカタカナの読み)
- 前文脈は無し (今の選択の後置再変換と同じ。選択の前の文字列の読みは分からない)。LLM の左文脈も無し
- 取消 (Esc・Backspace・Tab など) は、今の後置再変換の取消と同じく、逆変換の読みのかなの run に戻す
  (縮めて外した部分も run に戻す)。逆変換の読みが誤っていたときに、そのまま読みを打ち直して
  変換し直せる。元の表記のまま終えたいときは、候補の先頭 (元の表記) を確定する
- 範囲の伸縮 (候補選択中の ←→) は今の選択の後置再変換と同じく、選択の中だけで行う。
  → で縮めて外した部分は、読みのかなとして文書に残す (記憶の漢字の文節を縮めたときと同じ)
- 確定は今の候補選択の確定と同じ経路。確定後の記憶の扱いも今の選択の後置再変換と同じにする

### E. 学習

逆変換の読みは推測で、誤ること (「今日」→「こんにち」など) がある。読みを推測したままの文節が
学習に入らないよう、表記が変わった文節だけを学習する。

- 確定した文節ごとに、その読みの範囲が逆変換の語の境界で区切れ、その範囲の逆変換の表記の連結が
  確定した表記と同じなら、その文節は「変わっていない」として学習しない
- 変わった文節は今どおり文節の学習 (LEARN / LEARN2 の文節の組) を送る
- 範囲全体の句の学習 (LEARN2 の末尾の読み全体)・文節境界の学習 (LEARNSEG)・複合語の学習
  (LEARNWORD) は送らない。範囲の読みの一部が推測のままのため
- すべての文節が変わっていなければ、何も学習しない

### F. 採らなかった案

- ITfFnReconversion (TSF の再変換の機能) を実装し、アプリ・システムからの再変換の依頼を受ける。
  自分で変換キーを押す場合は今の経路で足り、依頼してくるアプリ (Word の再変換、CUAS 経由の
  IMM32 アプリ) での実機確認も要るため、本書の対象外とする。使う場面が無いため見送り (docs/roadmap.md の見送り・既知の問題)
- 逆引きの索引にすべての語 (かなだけの表記を含む) を入れる案。かなの表記は読みが決まっているので
  読みの辞書で引けば足り、索引のメモリが増えるだけのため
- 逆引きの索引を「表記 + 読み」をキーにした fst にする案。表記が先頭のキーは圧縮が効かず
  (約 70MB)、起動時の構築に約 4 秒かかったため
- 語の読みを索引の中の文字列の表に持つ案。検索は約 4 倍速いが (1 回約 1.5µs と約 6µs)、
  メモリが約 3 倍 (約 44MB) になり、選択 1 回の逆変換では速さの差が問題にならないため
- 逆変換の読みを複数 (N-best) 返して選ばせる案。読みの選び方の UI が要るので、まずは 1-best とし、
  誤った読みは Esc で戻して打ち直す
- 範囲全体を今どおり学習する案。誤った読みで学習が入るため

## 実装手順

各手順の後にビルドとテストが通ることを確かめる。

1. engine: 逆引きの索引 (dict.rs) と、待ち受け開始後の別スレッドでの構築 (main.rs)
2. engine: 逆変換 (reverse.rs)。下記のテストを入れる
3. engine: REVERSE (main.rs)、protocol.md
4. tsf: REVERSE の送受信、`ReadIdleTarget` / `ConvertIdleTarget` の逆変換の対象
5. tsf: 確定時の学習の絞り込み (E)
6. ドキュメントの更新
7. 手動テスト (下記)
