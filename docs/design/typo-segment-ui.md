# 文節 UI へのタイプミス補正

## 背景と目的

変換へのタイプミス補正 ([typo-conversion.md](typo-conversion.md)) は、入力全体の候補 (CONVNBEST・RERANK)
だけが対象で、文節 UI (設定 `segment_ui 1`) の CONVSEG・CONVCTX には入っていない。文節 UI で打ち間違えた
読みを変換すると、崩れた変換になるうえ、文節の区切りそのものが崩れる。

| 入力 | 今の CONVSEG の区切り | CONVNBEST の補正の候補 |
|---|---|---|
| よろしくおねぎあします | よろしく / 尾根 / ギア / します | よろしくおねがいします (1 文節) |
| あしたのきあぎはなんじからですか | 明日 / ノキア技は / 何時からですか | 明日の会議は / 何時からですか |
| きょうはいいてんくですね | 今日は / いい / 転句ですね | 今日は / いい天気ですね |

打ち間違えた語が文節をまたいで割れるため、文節の読みだけで補正を探す方式 (文節ごとの補正) では直せない。

本書の目的は、文節 UI の変換でも、入力全体の補正の最良経路に沿って文節を区切り、打ち間違えた語を含む文節の
候補に補正の表記を足すことである。

## 決定事項

### A. 補正の求め方 (エンジン)

- CONVSEG・CONVCTX の文節長の指定が無い変換で、CONVNBEST と同じラティス (補正の語のノード入り、
  2 状態の Viterbi。typo-conversion.md の A・B) を作り、通常の最良経路と補正の最良経路を求める
- Δ・しきい値 (`TYPO_COST`・`TYPO_SHOW`・`TYPO_TOP`) と、補正を作らない条件 (設定 `typo_correction` 0、
  かなが 3 文字未満、先頭のかな) は CONVNBEST と同じ
- 補正の語を足しても通常の最良経路は変わらないので、補正の候補が無いときの結果は今と同じ

### B. 文節の区切り

- Δ ≥ `TYPO_SHOW` のときは、文節を補正の最良経路から今と同じ規則 (`group_path`。数字の結合、付属語を前の
  自立語に付ける) で区切る。それ以外は今どおり通常の最良経路から区切る
- Δ < `TYPO_TOP` (補正を先頭にしない) ときも補正の経路の区切りに従う。通常の経路の区切りでは、文節の範囲が
  補正の語とずれて補正の表記を置ける文節が無いため。打ち間違いの無い文 144 件 (typo-conversion.md の
  「計測の結果」) では Δ ≥ `TYPO_SHOW` が 0 件なので、ふだんの区切りは変わらない
- 文節の読みは打ったかなの区間 (CONVNBEST の補正の候補と同じ)

### C. 補正の文節の候補

- 補正の語を含む文節 (補正の文節。補正の語は経路に 1 つなので、補正の文節は 1 つ) の候補は、その区間の
  通常の変換の候補に補正の表記 (補正の経路の文節の表記) を 1 件足したもの
  - 区間の通常の変換は、文節長を固定した変換 (`convert_segments_fixed`) と同じく、区間の読みだけの
    Viterbi の経路を `segment_from_group` に通して作る。前文脈は直前の文節 (先頭の文節なら要求の前文脈)
  - 補正の表記が通常の変換の候補に既にあれば足さない (補正の印も付けない)
- 位置:
  - 先頭: Δ ≥ `TYPO_TOP` で、かつ CONVNBEST で補正の候補を先頭に置く条件 (読み全体の学習表記が無く、
    通常の 1-best が学習・ユーザ辞書の語・英字を含まない) を満たし、さらに補正の文節の通常の変換の先頭が
    学習 (文節の学習・文脈学習) で変わっていないとき
  - それ以外は 2 番目 (通常の変換の先頭の直後)
- 補正の文節の後ろの文節の文脈学習は、今どおり直前の文節の先頭候補の表記で引く

### D. 文節の伸縮

- 文節長を指定した変換 (Shift+←→ で長さを固定した文節) には補正を入れない。指定された区切りを動かせず、
  短い読みでのしきい値も計測していないため
- 伸縮した文節より後ろは今も文節長の指定なしの CONVCTX で区切り直すので、A〜C がそのまま効く。
  伸縮した文節より前の文節は、補正の候補を含めて今の候補のまま残る

### E. プロトコル

- CONVSEG・CONVCTX の要求の末尾に、省略可能なフィールド `kinds` を足す。文節長と併用するときは文節長の後ろ:

```
要求:   CONVSEG\t<かな>[\t<文節長>][\tkinds]\n
        CONVCTX\t<文脈読み>\x1f<文脈表記>\t<かな>[\t<文節長>][\tkinds]\n
成功:   OK\t<文節1>\t<文節2>\t...\n
文節 = <読み>\x1f<候補1>\x1f<候補2>...
候補 = <表記>[\x1d<種類>]
```

- エンジンは文節長のフィールドが `kinds` なら、文節長の指定なしで `kinds` ありとして読む
- `kinds` があるときだけ A〜C の補正を行い、補正の表記の末尾に `\x1d` と種類 `typo` を付ける
- `kinds` が無ければ補正を行わず、今と同じ応答を返す。CONVNBEST (`kinds` が無くても補正の候補を印なしで
  返す) と違い、補正で区切りまで変わるので、印を読めない旧 TSF 層には補正の結果を渡さない
- 旧エンジンは `kinds` を文節長として読み、`ERR` (文節長が不正です) を返す。TSF 層は `kinds` を付けた要求が
  `ERR` になったら `kinds` を外して送り直し、以後そのエンジンには `kinds` を付けない

### F. TSF 層

- `ConversionSegment` に補正の表記の一覧 (`typoSurfaces`) を持たせる。候補の並びは
  `InsertRawCandidates`・`SyncPairedSegment`・`PlaceAdoptedCandidate` などで後から変わるので、候補と並行する
  配列ではなく表記で引く (入力全体の候補の補正の判定が表記で引くのと同じ)
- `kinds` を付けるのは、文節 UI の変換キー (`BuildConversionSegments` の `segmentUi`) と、伸縮した後ろの
  区切り直し (`ResizeSegment` の `ConvertSegments`) の CONVSEG・CONVCTX。文節長を固定した変換と、英字を
  含む入力の 1 文節固定の変換には付けない
- 候補一覧 (`ShowConversionPanel`) は、今の文節の候補のうち `typoSurfaces` にある表記を補正の候補
  (`ItemKind::Typo`) として出す。「補正」のタグと `typo` 色は segment_ui 0 の補正の候補と同じ

### G. 学習 (TSF 層)

- 補正の表記を選んだ文節の LEARN (文節の学習・文脈学習) は送らない。打ち間違えた読みで学習データを汚さない
  ため。ほかの文節は今どおり送る。ほかの文節の文脈は今どおり直前の文節の表記 (補正の表記を含む)
- 補正の表記を選んだ文節が 1 つでもあれば、読み全体の学習 (2 文節以上のときの読み全体 → 確定文字列) と、
  伸縮の学習 (LEARNSEG・LEARNWORD) を送らない。どちらも打ち間違えた読みを含むため
- 前文脈 (直前に確定した文節) と採用した文字列の記憶 (adopted-reconversion.md) は、ほかの候補と同じく
  打ったかなを読みとして更新する

## 実装手順

各手順の後にビルドとテストが通り、既存の動作が壊れていないことを確かめる。

1. engine: `convert_segments` の補正 (A〜C)。補正なしの結果が今と同じであるテストを先に足す
2. engine: CONVSEG・CONVCTX の `kinds` と応答の印 (E)。`kinds` 無しで今と同じ応答になるテスト
3. tsf: engine_client の `kinds`・送り直し・解析
4. tsf: 候補一覧の補正の表示と確定時の学習 (F・G)
5. ドキュメントの更新

## 検証方法

### 自動テスト (`cargo test`)

- `よろしくおねぎあします` の CONVSEG (`kinds` 付き) で、補正の文節の先頭に補正の表記が `\x1dtypo` 付きで出る
- 補正の文節の 2 番目以降に、その区間の通常の変換の候補が出る
- 打ち間違いの無い読み (`よろしくおねがいします`・`きょうははれです`) では、`kinds` の有無によらず応答が
  今と同じ
- `kinds` 無し・`typo_correction 0`・3 文字未満の読みでは補正が入らない
- 補正の文節の読みに学習があるときは補正の表記が 2 番目になる
- 文節長を指定した `kinds` 付きの要求では補正が入らない。文節長のフィールドが `kinds` の要求は文節長の
  指定なしとして読む

### 応答時間

- `typo_eval` の 705 読みで、CONVSEG (`kinds` 付き) の 1 回の時間 (中央値・最大) を補正なしと比べ、
  結果を本書に書く。変換キーと伸縮でしか呼ばないので、CONVNBEST の補正 (中央値 1.89ms) と同程度なら許容する

### 実機テスト

開発版 DLL に切り替え (scripts\dev-deploy.ps1 -Dll)、メモ帳で行う。`QUICKLIME_PIPE_NAME`・
`QUICKLIME_CONFIG_FILE`・`QUICKLIME_LEARN_FILE`・`QUICKLIME_USER_DICT_FILE` を隔離し、config に
`segment_ui 1`・`debug_log 1` を設定する。エンジンを release・debug の両方でビルドし直し、古いエンジン
プロセスが残っていないことと、メモ帳をプロセスごと終了してから開き直したことを確かめる。

| # | 操作 | 期待 |
|---|---|---|
| 1 | `yorosikuonegiasimasu` → 変換キー | 1 文節で、先頭の候補が補正の表記 (実辞書では 1 語の `よろしくおねがいします`)。候補一覧で「補正」のタグ付き |
| 2 | 1 の候補一覧を送る | 2 番目以降に `よろしくおねぎあします` を 1 文節に固定した通常の変換の候補 |
| 3 | `asitanokiagihanannjikaradesuka` → 変換キー | `明日の会議は` / `何時からですか` に区切られ、1 文節目の先頭が補正の候補 |
| 4 | 3 をそのまま確定 → 学習ファイルを見る | `あしたのきあぎは` の記録も、読み全体の記録も増えない。`なんじからですか` は記録される |
| 5 | 4 の後に同じ入力 → 変換キー | 今度も補正の候補が先頭に出る |

| 7 | 3 の状態で 1 文節目を Shift+← | 1 文節目は固定長の通常の変換になり補正の候補は消える。後ろは区切り直され、補正があれば後ろの文節に出る |
| 8 | 7 の後に確定 | LEARNSEG・LEARNWORD が送られない (debug_log で確認) |
| 9 | `typo_correction 0` で 1 | 今と同じ区切り (`よろしく` / `尾根` / `ギア` / `します`) で補正の候補が出ない |
| 10 | `segment_ui 0` で 1 | 今どおり入力全体の候補の補正 (typo-conversion.md) |
| 11 | 旧エンジン (本変更前) と新 DLL で 1 | 送り直しで今と同じ変換になり、変換が失敗しない |

## 計測の結果

`engine/examples/typo_eval.rs` の応答時間の節で計測した。

```
cargo run --release --example typo_eval -- --cases examples/data/llm_cases.tsv \
    --cases examples/data/typo_cases.tsv
```

- AMD Ryzen 5 9600X、Windows 11 Home、rustc 1.97.0 の release ビルド
- 辞書・学習・ユーザ辞書・前文脈・読み (705 読み) は typo-conversion.md の「計測の結果」と同じ
- エンジンのプロセスは起動せず `convert_segments` を直接呼ぶ (パイプの往復を含まない)。各読み 5 回、初回は除く
- 補正なしは `kinds` 無しの CONVSEG、補正ありは `kinds` 付きの CONVSEG に当たる

| 対象 | 補正 | 中央値 (ms) | 最大 (ms) | 最大の読み |
|---|---|---|---|---|
| convert_segments | なし | 0.07 | 0.34 | きろくをこうしんしゅた |
| convert_segments | あり | 1.23 | 6.78 | ちゅうもんをかくにんでぃました |
| convert_nbest (同じ回の参考) | なし | 0.33 | 5.06 | きしゃんこいしゃがきしゃできしゃした |
| convert_nbest (同じ回の参考) | あり | 1.65 | 8.13 | はいたつはごごになふぃます |

補正ありの CONVSEG は、同じ回の CONVNBEST の補正ありより中央値・最大とも小さい。
