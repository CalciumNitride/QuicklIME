# エンジンの早期起動

TSF 層がエンジン (quicklime-engine.exe) を、最初の変換より前に起動しておく。起動の途中に来た
変換はエンジンの準備ができるまで待ち、複数のアプリから同時に起動してもエンジンは1つだけにする。

## 背景と目的

今の自動起動 (docs/design/basics.md「エンジンの自動起動」) では、次の理由で PC の起動後の最初の変換が
失敗する。

- エンジンは辞書を読み終えてからパイプを作る。起動からパイプができるまで、ファイルがキャッシュに
  乗った状態の release 版で約 2.0〜2.1 秒かかる (PC の起動直後はもっと長い)
- TSF 層は、変換キーなどの明示的な変換で接続できないときにエンジンを起動し、最大2秒待つ。待ち時間が
  起動時間より短いため、初回は間に合わずに失敗する
- 起動の試行は 10 秒に1回までに抑えている。その間の変換は、パイプが開くのを待たずにすぐ失敗する
- 候補バー・ライブ変換・予測のような打鍵ごとの問い合わせではエンジンを起動しないので、最初の明示的な
  変換までは何も出ない

## 決定事項

### 起動だけしておく (待たない)

- `ActivateEx` で、パイプに接続できなければエンジンを起動する。起動の完了は待たない
  - ログオン時は explorer などのプロセスでも TSF がアクティブ化されるので、実際にはログオンと同時に
    エンジンが立ち上がる。スタートアップへの登録はしない
- 打鍵ごとの問い合わせ (ライブ変換・N-best のライブ版・予測・後続語予測・英字判定・RERANK) で
  パイプを開けなかったときも、エンジンを起動だけする。これまでどおり接続は待たず、その打鍵の問い合わせは
  失敗として扱う
- 起動の試行の間隔 (10 秒に1回まで) はどの経路でも共通にする

### 起動中なら待つ

- 明示的な変換などの待ってよい問い合わせ (`EnsureConnected` の経路) では、接続できないときに次のように
  する
  - 最後にエンジンのプロセスを起動できてから 5 秒以内なら、新たには起動せず、その時刻から 5 秒経つまで
    パイプが開くのを待つ (100 ms ごとに開いてみる)。exe が見つからないなどで起動できなかった試行は
    待つ対象にしない
  - それ以外なら起動を試み、5 秒まで待つ。10 秒の間隔の内側でまだ起動できないときは、待たずに失敗する
- 待ち時間の上限を 2 秒から 5 秒に延ばす。PC の起動直後の遅い辞書の読み込みでも間に合わせるため。
  早めの起動でエンジンがたいてい準備できているので、実際に5秒待つことはまれ
- 採らなかった案
  - 待ち時間を延ばすだけ: 最初の変換が毎回数秒止まる
  - パイプを先に作り、辞書の読み込み中の要求を待たせる: 打鍵ごとの問い合わせまで止まってしまう。
    読み込み中の応答を別に設けると、プロトコルと TSF 層の両方に手が入る
  - 辞書の読み込みを速くする (バイナリキャッシュなど): 効果は大きいが大がかりなので別の課題にする

### 二重起動の防止

- エンジンは起動の直後、辞書を読む前に、パイプ名から作る名前の named mutex (`Local\quicklime-engine-<パイプ名>`。
  パイプ名の `\` は `_` に置き換える) を作る。すでにあれば (`ERROR_ALREADY_EXISTS`)、ほかのエンジンが
  起動中か動作中なので何もせずに終了する。mutex はプロセスが終わるまで持ち続ける (終了時に OS が解放する)
- 今の「パイプに接続できたら終了する」チェックは残す。ただ、辞書の読み込み中はパイプが無いので、
  ログオン時のように多くのプロセスから同時に起動されると、それだけでは複数のエンジンが辞書を読んでしまう
- パイプ名ごとに mutex を分けるので、`QUICKLIME_PIPE_NAME` で隔離したエンジンは常用のエンジンと
  並んで動ける

## 変更対象ファイル

| ファイル | 変更内容 |
|---|---|
| tsf/src/engine_client.h, tsf/src/engine_client.cpp | 起動だけする入口 (接続を試み、開けなければ起動する。待たない)。打鍵ごとの問い合わせで開けなかったときの起動。`EnsureConnected` の「起動中なら待つ」と待ち時間 5 秒 |
| tsf/src/text_service.cpp | `ActivateEx` から起動だけする入口を呼ぶ |
| engine/src/main.rs | named mutex による二重起動の防止 |
| engine/Cargo.toml | windows-sys の feature が足りなければ足す (`Win32_System_Threading`・`Win32_Foundation`) |
| docs/design/basics.md | 「エンジンの自動起動」を新しい仕様に書き換え、本書へリンクする |

## 実装手順

各手順の後にビルドが通ることを確かめる。

1. エンジン: named mutex による二重起動の防止
2. TSF 層: `EngineClient` の起動だけする入口と、打鍵ごとの問い合わせでの起動
3. TSF 層: `EnsureConnected` の「起動中なら待つ」と待ち時間 5 秒
4. TSF 層: `ActivateEx` からの呼び出し
5. ドキュメント: basics.md

## 検証方法

`QUICKLIME_PIPE_NAME` などで隔離した PowerShell からメモ帳を起動して確かめる (.claude/CLAUDE.md
「エンジン検証の隔離」)。開発版 DLL に切り替え (scripts\dev-deploy.ps1 -Dll)、release の exe も
ビルドし直しておく。各ケースの前に、隔離したパイプ名のエンジンが動いていないことを確かめる。

### テストケース

| # | 操作 | 期待 |
|---|---|---|
| 1 | エンジンが無い状態でメモ帳を起動し、3 秒待ってから `kyouha` を打つ | 打鍵の途中から候補パネルに候補が出る。エンジンのプロセスが1つ動いている |
| 2 | エンジンが無い状態でメモ帳を起動し、すぐに `kyouha` → 変換キー | 少し待ってから変換候補が出る (失敗しない) |
| 3 | 2 の直後に、続けて別の語を変換する | すぐに変換できる |
| 4 | エンジンが無い状態で、隔離した PowerShell からメモ帳を5つ続けて起動する | エンジンのプロセスは最終的に1つだけ。起動中に2つ目以降が辞書を読まない (タスクマネージャでメモリが増えるのは1つだけ) |
| 5 | メモ帳を開いたままエンジンを終了 (`taskkill`) し、`kyouha` を打つ | エンジンが起動し直され、しばらくすると候補が出る。変換キーで変換できる |
| 6 | 隔離したエンジンを動かしたまま、常用の (隔離していない) メモ帳で入力する | 常用のエンジンにつながり、隔離したエンジンとは別に動く |
| 7 | エンジンの exe を見つけられない配置 (exe をリネームして退避) でメモ帳に入力し、変換キーを押す | 入力は止まらず、変換は待たずに失敗として戻る (かなのまま)。続けて変換キーを押しても待たない |
| 8 | エンジンを単体で2回続けて起動する | 2つ目は辞書を読まずにすぐ終了する |

## 未決事項

- 5 秒で足りるかは、PC の起動直後の実機で確かめる
