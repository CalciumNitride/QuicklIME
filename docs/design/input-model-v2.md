# 入力モデル v2 (総論)

本書は入力モデルの全面的な見直しの総論。原則・全体構成・段階の区切りと、段階をまたぐ
決定事項を定める。各段階の詳細設計は着手時に docs/design/ に別ファイルで起こし、
本書の「段階」の節から参照する。

## 背景と目的

direct 方式 (docs/design/direct-input.md) を作ったことで、Space をスペース専用にし、
変換を変換キーに分けられた。一方で、次の問題が残っている。

- ライブ変換で、途中まで正しかった前方の変換結果が後続の打鍵で書き換わる
- 連文節変換の訂正操作 (文節移動・伸縮・文節別の候補選択) が多い
- モードレス入力で判定を覆すたびに文書が書き換わる (チラつき・Undo)
- Enter が「改行・送信」と「確定」の2つの機能を兼ねている
- 空の入力欄の冒頭と、CUAS 経由のアプリ (WezTerm など) では composition 方式に
  フォールバックし、direct 方式が効かない
- キー割当を変えられる機能と、割り当てられるキーの形が限られている
- 統計変換の候補順位は、文脈による同音異義語の判別が弱い

これらを個別に直すのではなく、以下の原則に沿った入力モデルとして作り直す。

## 原則

- **P1. 文書に入った文字列を IME が自動で書き換えない。** 書き換えるのは、ユーザが
  候補を採用したときだけにする
- **P2. 1つのキーには1つの機能だけを持たせる。** Space はスペース、Enter はアプリの
  Enter (改行・送信)、変換キーは変換、確定キーは確定とする
- **P3. 入力方式は direct 方式に一本化する。** composition 方式は、段階2で
  フォールバックが不要になった時点で廃止する
- **P4. LLM はローカル推論だけで使う。** IME は全アプリの打鍵を扱うため、
  外部サービスへは送らない

## 決定事項

### 入力方式

- direct 方式をメインの入力方式にする
- 設定 `input_style` と composition 方式は、段階2の完了後に廃止する。それまでは
  既存の挙動を維持し、段階1・2の新しい挙動は direct 方式にだけ入れる
- 文節 UI (文節移動・伸縮・文節別の候補選択) は、段階4以降は設定でオンにしたときだけ
  使うオプションとして残す

### キーの役割

- Enter はコア操作として常にアプリへ渡す。候補選択中・サジェスト選択中は、
  確定してから Enter をアプリへ渡す (1 打で改行・送信まで進む)
- 確定キー (機能 `CommitRun`) を新設する。run 中は表示中の結果 (ライブ変換の結果を含む) で
  run を終え、末尾の未変換ローマ字は確定時と同じ救済を通す。候補選択中は確定する。
  既定の割当は無変換キー (VK_NONCONVERT)
- 確定キーを押さなくても、次の印字キーで暗黙に確定する (既存の挙動を維持する)
- Esc の run 中の意味 (文字を残して run を忘れる) は変えない

### キーマップ

- 機能への割当を「状態 x キー (修飾キー + 任意の仮想キー) → 機能」の表で持つ
- 状態は4つ: 入力なし / run 中 / 候補選択中 / サジェスト選択中
- 1つの機能に複数のキーを割り当てられる
- 設定 UI では、機能ごとの一覧に状態別の上書きを足す見せ方にする
- コア操作は割当変更の対象にしない (範囲は docs/design/keymap.md)

### フォールバック

- 空の入力欄の冒頭と CUAS 経由のアプリの両方で direct 方式が動くことを目標にする
- 方式は F1 を採る: 未完成のローマ字 (`k`) を文書に入れず、キャレット付近の小窓に出す。
  かなが完成した時点で文書に追記する。段階0a の試作で、未完成のローマ字だけを
  composition にする案 (F2) と比べ、使い勝手で F1 が勝った
- かなの入力は追記だけにする。置換は採用時とモードレスの英字切替時に限る

### LLM

- llama.cpp をエンジンプロセス内で動かす。TSF 層 (全アプリにロードされる DLL) には入れない
- GPU は特定のベンダーに依存させない (CPU と Vulkan。CUDA 専用にはしない)
- 主な役割は、入力全体の N-best 候補の順位補正とする。結果は候補バーへ非同期に反映し、
  打鍵を止めない
- 段階5で採用する。計測結果 (docs/design/experiment-0b-llm-results.md) で、遅延・メモリ・
  精度のいずれも見込みがある構成が確認できた。オプションとし、無効でも従来の統計変換だけで動く
- 構成は段階5で次の候補から選ぶ: CPU + zenz-v3.2-xsmall、Vulkan + zenz-v3.2-small / xsmall

### 段階0a: 追記型入力の実験

- F1 と F2 を隠し設定で切り替えられる試作を direct 方式に入れる
- 比べる観点: 打鍵の体感 (ローマ字が文書の外に出ることの違和感)、空の入力欄の冒頭での
  挙動、CUAS 経由のアプリ (WezTerm) での挙動、Chromium 系の不安定なフォーム
  (文字数固定・自動で次欄へ移動する欄) での安定性
- 採用しなかった方の試作コードは段階2で取り除く

### 段階0b: LLM の計測

- エンジンのクレートに example として、llama.cpp の Rust バインディングと zenz 系の
  かな漢字変換モデルを読み込み、読みと左文脈から変換結果を得る最小の試作を作る。
  エンジン本体と TSF 層には組み込まない
- 計測項目: GPU / CPU それぞれでの1回の推論の遅延、VRAM・RAM の使用量、
  モデルの読み込み時間
- 判断基準 (目安): 候補バーの更新が打鍵に追従できる遅延か、常駐させてよいメモリ量か

### 段階1: キーマップ刷新

- `KeyFunc` を全機能に広げ、状態別のキーマップ表に置き換える
- config.tsv の書式と設定ツールのキー入力欄を作り直す
- Enter の挙動と確定キーを「キーの役割」の決定事項どおりにする

### 段階2: フォールバック改善

- 0a で選んだ方式を本実装する
- フォールバック判定 (direct-input.md の「フォールバック判定」) を、追記型入力に合わせて
  作り直す
- 置換できない文書 (CUAS) での採用の方法を決める。最終手段は、Backspace の擬似打鍵を
  送ってから文字列を入れる方法
- composition 方式と設定 `input_style` を廃止する

### 段階3: 候補バー

- 入力中は横一列の候補バーを常時表示する。内容は入力全体の変換結果・予測候補・
  先頭部分の変換候補
- ライブ変換の結果は文書に入れず、候補バーに表示する (P1)。採用した部分だけが
  文書上で置き換わり、以後は変わらない
- 予測サジェストの縦の候補ウィンドウは候補バーに統合する
- 採用キーは変換キー・Tab 系・確定キーを基本にし、キーマップで変えられるようにする

### 段階4: 入力全体の N-best

- 入力全体を1単位として N-best 候補を生成する (エンジン)。意味の異なる候補が上位に
  並ぶよう、重複を抑える
- 学習は「読み全体 → 表記」を基本にする
- 文節 UI は設定でオンにしたときだけ使う

### 段階5: LLM による順位補正

- 段階4の N-best を LLM で並べ替え、候補バーへ非同期に反映する
- ユーザ辞書語や英字混じりの表記は保護し、LLM の出力で上書きしない
- 読みなしの後続語予測 (候補バーが空のときに次の語を出す) は、段階5の中で別途検討する

## 検証方法

- 各段階の設計ドキュメントにテストケースを記す
- 段階をまたいで共通して確認する項目:
  - メモ帳・Word・Chrome (通常の入力欄・空欄の冒頭・不安定なフォーム)・WezTerm で
    入力・変換・採用・確定ができること
  - Enter がどの状態でもアプリに届くこと (P2)
  - 文書に入った文字列が、採用操作なしに書き換わらないこと (P1。段階3以降)
