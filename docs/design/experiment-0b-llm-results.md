### 上流の llama.cpp で読み込むための上書き

GGUF の `tokenizer.ggml.pre` は `gpt2-small-japanese-char` で、上流の llama.cpp は
「unknown pre-tokenizer type」で読み込みに失敗する。azooKey が使う llama.cpp のフォーク
(azooKey/llama.cpp b4846 の src/llama-vocab.cpp) は、この値を GPT-2 と同じ正規表現の
前処理として扱っているだけなので、llm_bench はメタデータを `gpt-2` に上書き
(kv override) して読み込む。トークン化は同じ結果になる。

## 確認したプロンプトの書式

出典: azooKey/AzooKeyKanaKanjiConverter のコミット d59a28e4c7ca049aef04f29a91eae9677a7753f2
(2026-09-23)。

| ファイル | 確認した内容 |
|---|---|
| Sources/KanaKanjiConverterModule/ConversionAlgorithms/Zenzai/Zenz/ZenzPromptBuilder.swift | 区切りの文字と、zenz-v3 の評価用プロンプトの組み立て (`candidateEvaluationPrompt`)。左文脈は末尾 40 文字 (既定) |
| 同 Zenz.swift | 読みは `toKatakana()` でカタカナにしてから渡す |
| 同 ZenzContext.swift | 前処理 (半角スペースを U+3000 に、改行を削除)。プロンプトは `add_bos=true`・特殊トークン解釈なしでトークン化。n_ctx 512 |
| 同 ZenzCandidateEvaluator.swift | 候補はプロンプトと別にトークン化 (BOS なし) し、プロンプトの後ろに連結して評価する。出力の終わりは EOS |
| Package.swift | llama.cpp は azooKey/llama.cpp の b4846 (フォーク) |

zenz-v3 の書式 (本計測で使った形):

```
[U+EE02 <左文脈 (末尾 40 文字)>] U+EE00 <読み (カタカナ)> U+EE01 <出力> <EOS>
```

- 左文脈が空のときは U+EE02 と左文脈を省く
- 本計測で使っていない要素: 条件 (U+EE03 プロフィール、U+EE04 話題、U+EE05 文体、
  U+EE06 好み。各 25 文字)、右文脈 (U+EE07)、カーソル位置の区切り (U+EE08)。
  zenz-v2 系は区切りの順序が違う (U+EE00 読み U+EE02 文脈 U+EE01)
- このモデルはメタデータの `tokenizer.ggml.add_bos_token` が false のため、`add_bos=true` でも
  BOS は付かない (llama.cpp の挙動。azooKey も同じ)。区切りの私用領域の文字は語彙に無く、
  UTF-8 の 3 バイトがそれぞれ 1 トークンになる
- EOS はトークン ID 2 (`<s>`)

## 計測方法

- release ビルド。各条件でウォームアップ 5 回の後に 30 回測り、中央値と p95 (nearest-rank) を取った
- 計測の左文脈は「先週の話ですが、」で固定
- 生成: 貪欲法 (毎トークン argmax)。EOS か上限 (読みの文字数 x 2 + 8 トークン) で止める。
  入力の読みは 5 かな「あめがふる」、10 かな「きのうはあめがふった」、
  20 かな「きのうはあめがふったのでいえでねていた」
- 順位付け: 各候補の対数尤度 = 候補の全トークンと終端の EOS の log softmax の和。
  候補は llm_bench.rs に固定した 10 個 (「昨日は雨が降った」「昨日は飴が降った」…) の先頭 N 個
- KV キャッシュの扱いは 3 通り測った
  - 使い回さない: 候補ごとにキャッシュを捨て、プロンプト + 候補を 1 回で評価
  - 使い回す (候補を順に): プロンプトを 1 回だけ評価し、候補ごとにプロンプトより後ろを捨てて評価
  - 使い回す (候補を1バッチ): プロンプトを 1 回だけ評価し、そのキャッシュを候補数分の
    シーケンスへ複製して、全候補を 1 回の decode で評価
- コンテキスト: n_ctx 512、n_batch・n_ubatch 512、n_seq_max 16、KV キャッシュ統合 (kv_unified)、
  KV は f16 (既定)、flash attention は auto (CPU・Vulkan とも有効になった)
- Vulkan: 全層を GPU に載せる (n_gpu_layers 999)。トークン埋め込みだけは CPU に残る
  (llama.cpp の既定の配置)
- 読み込み時間: モデルの読み込み + コンテキスト作成。同じプロセスで 5 回。モデルファイルは
  事前に何度も読んでおり、OS のファイルキャッシュに載った状態 (ディスクからの冷えた読み込みは未計測)
- メモリ: プロセスのワーキングセット (WS) とプライベート (コミット)。GPU 専用メモリは
  パフォーマンスカウンタ「GPU Process Memory」の自プロセス分。読み込み時間の 2 回目以降の
  反復は推論の後に行い、ピークに混ざらないようにした

### 方式による対数尤度の差 (実装の検算)

「使い回さない」との対数尤度の最大差 (4 条件の全候補中)。1 位の候補は全条件で一致した。

| モデル | バックエンド | 使い回す (候補を順に) | 使い回す (候補を1バッチ) |
|---|---|---|---|
| small | CPU (2 / 4 / 6 スレッドとも) | 0.0000 | 0.5810 |
| small | Vulkan | 0.1685 | 0.1010 |
| xsmall | CPU (2 / 4 / 6 スレッドとも) | 0.0000 | 0.3873 |
| xsmall | Vulkan | 0.1090 | 0.0936 |

- 1 バッチ形で差が出るのは、論理的な誤り (シーケンス間の注意の漏れ) ではなく数値誤差と判断した。
  切り分けとして、別シーケンスに置いた詰め物の候補の「内容」を変えても値は変わらず、
  「長さ」(= KV セル上の配置) を変えたときだけ変わった。スレッド数・KV を f32 にしても残り、
  flash attention の有無だけでも候補あたり最大 0.3 程度値が動く。量子化モデルの行列積で活性を
  8 bit に量子化する際の丸めが、総和順序の違いを増幅していると考えられる
- 対数尤度の差が 0.1〜0.6 程度の候補どうしは、計算の形やバックエンドで順位が入れ替わりうる
  (精度確認でも xsmall の #23 が CPU と Vulkan で入れ替わった)

### 精度

テストセット engine/examples/data/llm_cases.tsv (50 件。左文脈あり 35 件、左文脈なし 15 件)。

- 統計 1-best: 隔離して起動したエンジン (現行 HEAD のソースを release ビルド) に、読みだけで
  CONVERT を送った第 1 候補。CONVSEG の各文節の第 1 候補の連結とも比べ、異なったのは
  「いった」の 2 件だけ (CONVERT「一田」、CONVSEG「いった」。どちらも不正解)
- LLM 順位1位: テストセットの候補群の対数尤度で 1 位の候補 (「使い回す (候補を順に)」で計算)
- LLM 生成: 貪欲法の生成結果がそのまま正解と一致したか

| モデル | 条件 | 区分 | 統計 1-best | LLM 順位1位 | LLM 生成 |
|---|---|---|---|---|---|
| small | CPU 6スレッド | 全体 (50 件) | 25/50 (50%) | 44/50 (88%) | 46/50 (92%) |
| small | CPU 6スレッド | 左文脈あり (35 件) | 16/35 (46%) | 32/35 (91%) | 33/35 (94%) |
| small | CPU 6スレッド | 左文脈なし (15 件) | 9/15 (60%) | 12/15 (80%) | 13/15 (87%) |
| small | Vulkan | 全体 (50 件) | 25/50 (50%) | 44/50 (88%) | 46/50 (92%) |
| small | Vulkan | 左文脈あり (35 件) | 16/35 (46%) | 32/35 (91%) | 33/35 (94%) |
| small | Vulkan | 左文脈なし (15 件) | 9/15 (60%) | 12/15 (80%) | 13/15 (87%) |
| xsmall | CPU 6スレッド | 全体 (50 件) | 25/50 (50%) | 43/50 (86%) | 38/50 (76%) |
| xsmall | CPU 6スレッド | 左文脈あり (35 件) | 16/35 (46%) | 30/35 (86%) | 27/35 (77%) |
| xsmall | CPU 6スレッド | 左文脈なし (15 件) | 9/15 (60%) | 13/15 (87%) | 11/15 (73%) |
| xsmall | Vulkan | 全体 (50 件) | 25/50 (50%) | 42/50 (84%) | 38/50 (76%) |
| xsmall | Vulkan | 左文脈あり (35 件) | 16/35 (46%) | 30/35 (86%) | 27/35 (77%) |
| xsmall | Vulkan | 左文脈なし (15 件) | 9/15 (60%) | 12/15 (80%) | 11/15 (73%) |

比較の前提:

- 統計 1-best には左文脈を渡していない (仕様どおり読みだけで CONVERT/CONVSEG を送った)。
  テストセットの左文脈は表記だけで読みが無く、CONVCTX には使えないため。左文脈ありの 35 件は
  LLM に有利な比較で、条件がそろうのは左文脈なしの 15 件
- 候補群は実装者が手で作ったもので、エンジンの N-best ではない。統計 1-best は候補群の外の
  表記 (「一田」「記者下」など) になることがある
- テストセットは実装者が典型例で作った初版で、件数も少ない

## 判断基準との照合

仕様の「判断基準 (目安)」と照らした事実だけを記す。採否の判断はしていない。

- 順位付け N=10・読み 20 かなの p95 が 50 ms 以下
  - 満たした: Vulkan の small (1バッチ 15.85 / 順に 37.96 / 使い回さない 45.99)、
    Vulkan の xsmall (3 方式とも 20.04 以下)、CPU 6 スレッドの xsmall の 1バッチ形 (45.09)
  - 満たさなかった: CPU の small (最良は 6 スレッド・1バッチ形の 154.21)、
    CPU の xsmall のそれ以外 (4 スレッド・1バッチ形 52.86、6 スレッド・順に 57.83 など)
- 常駐による追加メモリが 300 MB 以下 (推論の後の値から開始時の値を引いたもの)
  - CPU の small: WS +102.4、私用 +69.2 (6 スレッド)
  - CPU の xsmall: WS +40.5、私用 +51.9 (6 スレッド)
  - Vulkan の small: WS +213.1、私用 +255.0 に加えて GPU 専用 119.4。プロセスのピークは私用 291.0
  - Vulkan の xsmall: WS +124.4、私用 +164.9 に加えて GPU 専用 57.8
- 精度が統計変換の 1-best より明らかに良いこと
  - 本テストセットでは、全体で統計 50% に対し LLM 順位1位 84〜88%・生成 76〜92%。
    条件がそろう左文脈なしの 15 件では、統計 60% に対し LLM 順位1位 80〜87%・生成 73〜87%
  - 前提 (統計に左文脈を渡していない、候補群が手作り、件数が少ない) は上記「比較の前提」のとおり

## 再現手順

### ビルド

CPU のみ (エンジンの通常ビルドとは別の feature):

```
set LIBCLANG_PATH=C:\Program Files\LLVM\bin
set PATH=<VS>\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin;%PATH%
cd engine
cargo build --release --example llm_bench --features llm-bench
```

Vulkan:

- Visual Studio ジェネレータでは、llama.cpp の vulkan-shaders-gen (ExternalProject) の
  configure・build・install が並行して走り、順序が崩れて失敗した。cmake クレートが読む
  環境変数 `CMAKE_GENERATOR=Ninja` で Ninja を使い、vcvars64.bat で MSVC の環境を整えてビルドした
- engine/target 配下のような長いパスでは、try-compile のパスが 260 文字を超えて C1083 で失敗した。
  `subst` で一時ドライブを target ディレクトリに割り当て、`--target-dir <ドライブ>:\` で
  ビルドしてから割り当てを外した

```
call "<VS>\VC\Auxiliary\Build\vcvars64.bat"
set LIBCLANG_PATH=C:\Program Files\LLVM\bin
set VULKAN_SDK=C:\VulkanSDK\1.4.363.0
set PATH=%VULKAN_SDK%\Bin;<VS>\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin;<VS>\Common7\IDE\CommonExtensions\Microsoft\CMake\Ninja;%PATH%
set CMAKE_GENERATOR=Ninja
subst Q: D:\project\QuicklIME\engine\target\x
cd /d D:\project\QuicklIME\engine
cargo build --release --example llm_bench --features llm-bench-vulkan --target-dir Q:\
subst Q: /d
```

### 実行

統計変換の 1-best を取るエンジンは、パイプ名・学習・ユーザ辞書・設定・インポート辞書を
空のファイル / ディレクトリに向けて隔離して起動した (`QUICKLIME_PIPE_NAME`、
`QUICKLIME_LEARN_FILE`、`QUICKLIME_USER_DICT_FILE`、`QUICKLIME_CONFIG_FILE`、
`QUICKLIME_IMPORT_DIR`、辞書は `QUICKLIME_DICT_DIR` で references/mozc の dictionary_oss)。

```
llm_bench --model <gguf> --backend cpu --threads 2|4|6 --mode bench --cases examples/data/llm_cases.tsv
llm_bench --model <gguf> --backend cpu --threads 6 --mode all --engine --cases examples/data/llm_cases.tsv
llm_bench --model <gguf> --backend vulkan --threads 6 --mode all --engine --cases examples/data/llm_cases.tsv
```

`--engine` を付けるときは `QUICKLIME_PIPE_NAME` に隔離したエンジンのパイプ名を指定する。
反復回数の既定はウォームアップ 5 回・計測 30 回・読み込み 5 回。
