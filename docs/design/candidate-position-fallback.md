# 入力位置が得られないアプリでの候補ウィンドウの位置

## 背景と目的

候補ウィンドウ・未完成ローマ字の小窓・候補バーは、TSF から得た文字位置
(composition の矩形 / 選択範囲の矩形) を基準に表示している。

ゲームのマビノギ (CUAS 経由・追記のみの文書) で次を実測した。

- TSF が返す矩形は常に `(3439,1391)` で、主モニタ (3440x1440) の右下隅に丸められた値だった。
  ゲームのウィンドウは別モニタ `(15,1440)-(2575,2880)` にあり、入力欄とは無関係の位置である
- システムキャレットは無い。IMM32 の位置 (ImmGetCompositionWindow / ImmGetCandidateWindow) は
  取得に失敗する。入力欄の位置を知る手段は無い
- 候補ウィンドウと小窓はモニタの外へはみ出して表示され、利用者から見えなかった。
  ウィンドウの作成・表示・描画は正常に行われていた

目的は次の 2 つ。

- 入力位置が明らかにおかしいアプリでも、候補ウィンドウ・小窓・候補バーが見える場所に出るようにする
- どのアプリでも、これらのウィンドウがモニタの外へはみ出さないようにする

## 決定事項

### 位置の妥当性判定と代わりの位置

- 文字位置から求めた基準矩形 (下記の「対象」) が文書のウィンドウの外にあれば、無効とみなす
  - 文書のウィンドウ: `ITfContext::GetActiveView` → `ITfContextView::GetWnd` で得た HWND の
    `GetAncestor(GA_ROOT)`。得られなければ `GetGUIThreadInfo(GetCurrentThreadId())` の
    hwndFocus (無ければ hwndActive) のルートを使う。どちらも得られなければ判定しない (今の挙動のまま)
  - 判定には基準矩形の左上の点 `(left, top)` を使う。その点がルートウィンドウの `GetWindowRect` の
    中に無ければ無効とする (幅・高さ 0 の矩形も扱えるように点で判定する)
- 無効なときの代わりの位置は、ルートウィンドウの中央の点 (幅 0・高さ 0 の矩形) とする。
  候補ウィンドウ・小窓・バーは、今と同じくこの点を基準に配置する (候補ウィンドウはその下など)
- 対象
  - `TextService::CandidateAnchor` (候補ウィンドウ): TSF から得た矩形、キャレット、マウス位置の
    どの経路で決めた矩形にも、最後に判定を適用する。小窓の下端に合わせる既存の補正は、判定の後に行う
  - `TextService::CaretRect` (小窓・候補バー): 取得に成功した矩形に判定を適用する。
    取得に失敗した (false を返す) 場合の扱いは変えない
- 判定と代わりの位置の計算は 1 つの関数にまとめ、両方から呼ぶ

採らなかった案

- マウスカーソル付近に出す: マビノギではマウスをキャラクターの操作に使うため、入力欄と無関係な
  位置になりやすい
- 固定位置を設定で指定できるようにする: 今回の利用者の要望ではない。必要になったら追加する
- 候補をゲームに渡して描かせる (`ITfCandidateListUIElement`): MS-IME・Google 日本語入力・ATOK は
  この方式だが、QuicklIME 自身の UI (未完成ローマ字の小窓・候補バーを含む) を使い続ける方針とした

### 作業領域への収め込み

- `CandidateWindow::Show` (縦の候補一覧) と `CandidateWindow::ShowInline` (小窓) で、計算した
  ウィンドウの矩形を、基準点を含むモニタ (`MonitorFromPoint(..., MONITOR_DEFAULTTONEAREST)`) の
  作業領域 (`rcWork`) の中に収める
  - 右にはみ出す場合は左へずらす。下にはみ出す場合は、基準矩形の上側 (anchor.top の上) に出し、
    それでもはみ出す場合は作業領域の下端に合わせる。左・上にはみ出す場合は作業領域の端に合わせる
- `CandidateWindow::ShowBar` は既に作業領域に収めているので変えない

### 診断ログの整理

調査のために足した診断ログのうち、次のように扱う。

- 残す: キー (OnTestKeyDown / OnKeyDown / OnTestKeyUp / OnKeyUp / OnPreservedKey) の行、位置の
  出所 (「候補ウィンドウの位置」「小窓の位置」) の行、`CandidateWindow` の Show 系 / Hide /
  最初の WM_PAINT / WM_DESTROY の行
- 足す: 位置を無効と判定して代わりの位置を使ったとき、その旨と元の矩形・ルートウィンドウの矩形・
  代わりの位置を 1 行出す
- 削除: `TextService::LogWindowDiagnostics` (GUIThreadInfo・IMM・DPI の行) と、そのための
  imm32 のリンク (tsf/CMakeLists.txt) と `<imm.h>` の include。1 打鍵ごとに複数行出て多すぎ、
  調査は済んだため

## 変更対象ファイル

- tsf/src/text_service.cpp: `CandidateAnchor` に判定を適用する
- tsf/src/text_service_direct.cpp: `CaretRect` に判定を適用する。判定の関数を置く。
  `LogWindowDiagnostics` を削除する
- tsf/src/text_service.h: 判定の関数を宣言する。`LogWindowDiagnostics` の宣言を削除する
- tsf/src/candidate_window.cpp: `Show` と `ShowInline` を作業領域に収める
- tsf/CMakeLists.txt: imm32 のリンクを削除する

## 実装手順

1. 文書のルートウィンドウを得て、基準矩形を判定し、必要なら代わりの位置に置き換える関数を作る
2. `CandidateAnchor` と `CaretRect` から呼ぶ
3. `Show` と `ShowInline` に作業領域への収め込みを入れる
4. 診断ログを整理する
5. Debug と Release をビルドする

## 検証方法

テストケース

| # | 環境 | 操作 | 期待 |
|---|---|---|---|
| 1 | マビノギ (ボーダーレス・サブモニタ) | `kyouha` と打つ | 小窓・候補バーがゲーム画面の中央付近に見える |
| 2 | マビノギ | 続けて Convert | 候補ウィンドウがゲーム画面の中央付近に見え、Space / Convert で選択が動く |
| 3 | マビノギ (ウィンドウモード) | 1・2 と同じ | ゲームのウィンドウの中央付近に出る |
| 4 | マビノギ | 1・2 の後にデバッグログを見る | 代わりの位置を使った旨の行が出ている |
| 5 | メモ帳 | 入力・変換 | 今までどおりキャレット付近に出る (代わりの位置の行が出ない) |
| 6 | メモ帳を画面の右下端に寄せる | 行末で入力・変換 | 候補ウィンドウ・小窓が画面からはみ出さず、作業領域の中に収まる |
| 7 | Chrome・WezTerm | 入力・変換 | 今までどおりの位置に出る |
