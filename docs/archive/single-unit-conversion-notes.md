# 連文節変換をやめる方針の検討 (草案)

作成日: 2026-10-07

本メモは、増井俊之氏の主張を踏まえて連文節変換をやめ、文節をユーザに見せない変換へ
転換する案の調査結果と方針の草案。**方針は未決定で、コードは未着手**。
他の変更と合わせて検討し、採用が決まったら docs/design/ に設計ドキュメントを起こす。

## 増井俊之氏の主張

### 「連文節変換 considered harmful」

IM2016 発表資料と産業技術大学院大学講演 (2019/8/27) で、連文節変換の問題点を次の5つにまとめている。

| # | 問題点 | 氏の挙げた例・補足 |
|---|---|---|
| 1 | 正確な入力が必要で、間違いが許されない | 正確に打てない人には使えない。IoT 時代に向かない |
| 2 | 読みが長くても全部入力が必要 | 「品川駅まで」に `shinagawaekimade`。予測式なら `shinag` `mad` で足りる。高速・正確に打てるのは手指が器用な熟練者が座っているときだけ |
| 3 | 本質的に誤り訂正が必要 | 「きょうはいしゃにいった」は正しく変換しようがない (歯医者? 医者?)。訂正に文節選択などの余計なキー操作が要る。曖昧入力アルゴリズムを適用しにくい |
| 4 | カスタマイズが面倒 | 単語登録が面倒。他のシステムと辞書を共有しにくい |
| 5 | 標準語の日本語でしか使えない | 大阪弁 (「行かはる」) や他国語と併用できない |

まとめとして「間違いが許されない / 必要な操作が多い / 訂正が必須 / カスタマイズが難しい /
日本語の標準語でしか使えない ⇒ 良い点がほとんど存在しない」としている。
講演では、連文節変換を「思考が必要な不便なもの」、予測変換を「そもそも思考の成功例」に分類している。

### 代わりに氏が使う方式 (Gyaim / Slime / Chaim)

- 単純な予測変換。入力した読みに前方一致する候補を並べて選ぶ。確定した単語は候補の先頭に持ってくる
- 「接続辞書」: 単語ごとに 読み / カテゴリ / 接続カテゴリ (後ろに続き得るカテゴリ) を登録する。
  品詞の登録や自然言語処理は使わない
  - 単語の連結はする (`けいおうだ` の時点で「慶應大学」が候補に出る。活用は
    「結」+「べ」+「ない」、数詞は「三十五人」のように接続で組み立てる)
  - 連結は候補生成のためだけで、文節をユーザに見せたり区切り直させたりはしない
  - 探索は、読みの完全一致・前方一致・接頭部一致からの接続先の再帰探索だけの単純なもの
    (GyaimMotion の ConnectionDict.rb)
- 未登録語は、選択して読みを入れて確定すると登録される (入力・検索・登録の融合)
- 本人は10年以上この方式だけで生活しており、「それなりに使い物になる」としている

### QuicklIME に当てはめるときの注意

- 問題点 1・2・5 はモバイル・IoT・曖昧入力を主な対象にしている。PC キーボードでローマ字入力する
  QuicklIME では効き目が下がる
- QuicklIME に強く当てはまるのは 3 (訂正操作のコスト) と、2 のうち予測で省入力できる部分
- 氏が否定しているのは「長い入力を一括変換し、文節単位で訂正させる操作モデル」であり、
  単語を連結して候補を作ること (Viterbi による経路探索に相当) ではない

## QuicklIME の現状

文節を前提にした仕組みがエンジン・TSF 層の両方に広く入っている。

- プロトコル: CONVSEG / CONVCTX / LEARNSEG / LEARNWORD (docs/protocol.md)
- TSF 層: 文節移動 (←→)、文節伸縮 (Shift+←→)、文節別の候補選択。
  `tsf/src/text_service.cpp`、`tsf/src/text_service_direct.cpp`、`tsf/src/engine_client.cpp`
- エンジン: `engine/src/convert.rs` の文節化・固定区切りでの再変換・数字列の1文節化・
  文節境界の学習補正
- 周辺機能: 対記号の両側同期、ライブ変換 (毎打鍵の CONVSEG)

移行先に使える既存部品:

- PREDICT (短縮よみ → 履歴 → 辞書の前方一致予測。タイプミス補正付き)
- CONVERT (入力全体の候補リスト)

ただし CONVERT の文変換候補は Viterbi の 1-best のみで、2位以降は読み全体の辞書完全一致しかない。
このままでは「きょうはいしゃ」に対して「今日は医者」を候補に出せないため、
入力全体の N-best 生成が新たに必要になる。

## 方針案

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 入力全体を1単位で候補化 (推奨) | Space で入力全体を1単位として N-best 候補リストから選ぶ。文節 UI は廃止。予測サジェストを主役にし、短く打って確定するスタイルを前提にする | 氏の主張の核心 (訂正のための文節操作をなくす) を満たす。既存の Viterbi・辞書・PREDICT を活かせる | 長い入力では組み合わせが増え、望む候補が出にくい。N-best の実装と候補の多様性の確保が必要 |
| B. Gyaim 方式への置き換え | 接続辞書型の単純探索に置き換え、品詞・連接コストを使わない | 思想に最も忠実で単純 | Mozc 辞書の品詞・コストという資産を捨てる。変換精度が大きく下がるおそれがある |
| C. 既定のみ変更 | 既定の操作を A にし、文節 UI はオプションとして残す | 移行リスクが小さい | 転換にならず、コードの複雑さが残る |

### 案 A を採る場合の論点

1. N-best の作り方: N-best Viterbi か、1-best 経路の一部の語を入れ替える方式か。
   「医者 / 歯医者」のように意味の異なる候補が上位に並ぶよう、重複の抑え方も決める
2. 長い入力の扱い: 長く打たせない前提にする (予測サジェストで早めに確定させる) か、
   長い入力は自動で区切って先頭だけ確定させるか
3. 不要になる仕組みの扱い
   - 文節移動・伸縮、LEARNSEG、CONVCTX / LEARNWORD の文節前提部分は削除候補
   - 対記号の同期は単位全体の候補化で不要になる可能性が高い
   - ライブ変換は 1-best 表示としては残せる
4. 学習の単位: 「読み全体 → 表記」で学習する。Gyaim の「確定したものを先頭へ」と同じ考え方で、
   現状の learning.tsv と相性がよい
5. direct 方式との関係: run 単位の後置変換はもともと選択範囲全体の変換に近く、むしろ単純になる
