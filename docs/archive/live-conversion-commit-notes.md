# ライブ変換結果を途中で確定する手段の検討 (草案)

作成日: 2026-10-07

本メモは、direct 方式 + ライブ変換で「途中までは正しかったライブ変換結果が、後続の打鍵で
変わってしまう」問題への方針の草案。**方針は未決定で、コードは未着手**。
他の大規模変更 (docs/archive/single-unit-conversion-notes.md など) と合わせて検討し、
採用が決まったら docs/design/ に設計ドキュメントを起こす。

## 背景と問題

direct 方式でライブ変換が有効なとき、run は Space・Enter・編集キーなどで終わるまで続き、
毎打鍵で run の確定済みかな (`composer_.ConfirmedKana()`) 全体を CONVSEG/CONVCTX で
変換し直して surface を置き換える (`RunDisplayText` → `LiveDisplayText`)。
そのため、長い run では前方の文節が後続の打鍵による再計算で別の変換に変わることがある。

例: `kisyanokisyagakisyasuru` を打つ途中で「記者の汽車が」まで正しく出ていても、
続きを打つと前方が「貴社の記者が」などに変わり、変換キーで候補選択に入って直すことになる。

問題は2つに分けられる。

- 予防: 正しいと分かった時点で、その結果を以後の打鍵の影響から外したい
- 回復: 変わってしまった後に、前の結果へ戻したい

## 現状の確認

direct 方式の run 中 (候補選択・サジェスト選択でない状態) の Esc は、表示中の文字列を
文書に残したまま `EndRun()` する (text_service_direct.cpp `HandleKeyDirect` の VK_ESCAPE)。
`EndRun()` は `liveSegments_` があれば文節ごとに LEARN を送り、最後の文節を文脈にする。
つまり **実装上は既に「Esc = ライブ変換結果で確定」になっている**。

ただし、これは問題の解決になっていない。

- 「run を忘れる」操作としての位置付けで、確定操作として意識しにくい
- composition 方式の Esc (かな表示に戻してライブ変換を停止) と意味が逆
- 末尾の未変換ローマ字 (「今日h」の h) は Commit() の救済を通さずそのまま残る
- 予防にしか使えない。変わってしまった後は使えない

## 方針案

### 案A: 明示的な確定キー

run を終えて表示中の結果で確定するキーを、機能として正式に持たせる。

- 機能 `KeyFunc::CommitRun` (設定キー名は仮に `key.commit`) を追加する
- キーの候補: 無変換 (VK_NONCONVERT)、Shift+Enter、Ctrl+Enter、Esc の正式化
  - 無変換は JIS 配列で親指の位置にあり、direct 方式では変換キーと対になって覚えやすい。
    US 配列向けの代替が別に要る
  - Shift+Enter / Ctrl+Enter はアプリ側で意味を持つ (チャットの改行・送信) ため衝突しうる
  - Esc の正式化は追加実装が最小。確定前に `RunCommitText()` を通して未変換ローマ字を
    救済する形に揃える
- 確定後の打鍵は新しい run になり、文脈補正 (`SetCommitContext`) で前の run の文脈を引き継ぐ
- 長所: 単純で予測可能。エンジン変更なし
- 短所: 「変わる前に押す」必要があり、回復には使えない。打鍵の流れが1キー止まる

### 案B: 句読点で run を自動的に区切る

「、」「。」などの句読点を打った時点で、その文字までを確定して run を終え、以降を新しい
run にする。文脈は引き継ぐ。

- 長所: 追加の操作なしで run が文単位・句単位に短くなり、揺れの範囲が限定される。
  多くのユーザの入力の区切りと一致する
- 短所: 句読点をまたいで変換キーで直せなくなる (前の run の漢字は後置再変換の対象外)。
  確定アンドゥ (Ctrl+Backspace) で戻せるのは直前の run だけ
- 数字列中の「.」「,」(小数・桁区切り) を区切りにしないよう、区切りはローマ字テーブルが
  句読点を出力したときに限る必要がある
- 設定でオン/オフできるようにする (既定値は未決)

### 案C: 前方の文節を自動で固定する

一定の条件を満たした前方の文節を、以後のライブ変換で変えないようにする。

固定の条件の候補:

- 後ろに k 文節以上 (例: 2文節) 続いた文節
- 連続 n 打鍵 (例: 3打鍵) の間、表記と文節境界が変わらなかった文節

実現方式は2つある。

- C1: TSF 層で run を分割する。固定した文節を確定扱い (LEARN・文脈更新) にして run から
  切り離し、残りの読みで run を続ける。エンジン変更なし。`RomajiComposer` に先頭のかなを
  切り離す操作が要る。固定部分は変換キーで直せなくなる
- C2: run は1つのまま、固定した文節をエンジンに制約として渡す。CONVCTX の文節長指定を
  拡張し、「先頭 m 文節は指定の読み・表記で固定」を指定できるようにする (プロトコル変更)。
  変換キーでの候補選択では固定を外せば、固定部分も従来どおり直せる

- 長所: 操作が要らない。予防が自動で効く
- 短所: 後続の打鍵で前方を変えるのが正しいケース (「きしゃ」の曖昧性が後ろで解ける等) で
  かえって誤変換が残る。固定の条件次第で体感が大きく変わり、調整が必要

### 案D: 直前のライブ変換結果へ戻す (回復)

打鍵ごとのライブ変換結果を run 内で履歴として持ち、前方の文節が変わったとき、
キー1つで「変わる前の前方の文節 + 今の後方」に戻す。

- 戻した前方は案C の固定状態にする (戻した直後の打鍵でまた変わらないように)
- 長所: 回復ができる唯一の案
- 短所: 「どこまでが前方か」の定義 (変化前後の文節の対応付け) が難しい。操作の意味が
  ユーザに伝わりにくい。実装量が最も多い

### 案E: 確定・未確定の区別をなくし、常時表示の候補バーで選ぶ

案A〜D は「run = IME が打鍵ごとに書き換える範囲」を前提にしている。問題の根は、
direct 方式の run が見た目は確定済みでも、実質的には未確定文字列として扱われている点にある。
案E ではこの前提をやめ、ひらがなIME (Esrille) と同じく確定・未確定の区別をなくす。
さらにライブ変換の結果を文書に入れず、候補バーに表示する。

#### 原則

- 文書に入った文字列は、IME が自動で書き換えない。書き換えるのは、ユーザが候補を
  採用したときだけ
- 打鍵したかなはそのまま文書に入る (今の direct 方式の打鍵と同じ)
- ライブ変換の結果・予測候補・変換候補は、文書ではなく候補バーに常時表示する。
  採用した部分はそれ以後変わらない

これにより「正しかった結果が後で変わる」は原理的に起きない。正しいときに採用すれば
固定され、採用しなければ文書はかなのまま残る。

#### 候補バー (モバイルの入力システム風の UX)

従来の「変換キーを押すと出る縦の候補ウィンドウ」ではなく、入力中は常に横一列の
候補バーを出しておく。

- 表示する内容 (並び順は要検討):
  1. 入力中のかな列全体の変換結果 (今のライブ変換結果にあたる)
  2. 予測候補 (PREDICT。前方一致。「しながわ」→「品川駅まで」のように、読みを最後まで
     打たずに選べる)
  3. 先頭文節だけの変換候補 (長い入力を前から順に片付ける用途)
- 採用の操作 (Space は direct 方式ではスペースのままにする):
  - 変換キー: 先頭の候補 (= 全体の変換結果) を採用する
  - Tab / Shift+Tab: 候補バー上の選択を動かす。選択中の候補は変換キーか Enter で採用する
  - 数字キーは数字の入力と衝突するため、番号選択には修飾キーが要る (Ctrl+1〜9 など)
- 採用後の処理:
  - 採用した候補の読みに当たる部分を文書上で置き換え、残りのかなは入力中のまま残る
    (先頭文節だけを採用した場合)
  - 採用時に LEARN を送る (run 終了時ではなく採用時が学習の契機になる)
  - 入力中のかなが空になったら、次の語の予測 (前文脈からの後続語予測) を出すことも
    考えられる。モバイルの入力システムや増井氏の POBox 系に近い使い方で、
    エンジンに新しい要求 (読みなしの後続語予測) が要る
- 表示位置: キャレット行のすぐ下か上に、ウィンドウを非アクティブのまま重ねて出す。
  打鍵ごとに位置や幅が大きく揺れると読みにくいため、位置は run の先頭に固定する。
  ブラウザの入力補完ドロップダウンと重なりうるので、行の上に出す選択肢も持つ
- 今の予測サジェスト (縦の候補ウィンドウ + Tab) とライブ変換は、どちらも候補バーに
  まとめられる

#### 変換対象の範囲

- 候補バーの対象は「入力中のかな列」= 最後に採用した位置 (または run の先頭) から
  キャレットまで。今の run の記憶をそのまま使う
- run が途切れた後 (キャレット移動など) は、キャレット直前のかな列を文書から読んで
  対象にできる (今の後置再変換を、選択なしでも動くように広げる形)。対象の範囲を
  変えたいときは Shift+←→ で伸縮する
- 漢字を含む部分を読みなしで直すには、IME が読みを覚えている必要がある。採用した
  文字列とその読みを、文書と一致する間だけ覚えておく (今の run 照合の仕組みを流用する)

#### 長所

- ライブ変換の「押さなくても変換結果が見える」体験を、文書を書き換えずに残せる
- 予測入力を中心に据えられる。読みを省略して選ぶ入力が自然にでき、増井氏の主張
  (docs/archive/single-unit-conversion-notes.md) の方向と一致する。連文節変換を残すか
  やめるかに関係なく、候補バーの中身の作り方だけで切り替えられる
- 打鍵中は文書を1回挿入するだけで済み、打鍵ごとの置換が減る
  (「アプリの Undo 履歴に置換が1打鍵ごとに積まれる」という既知のトレードオフが軽くなる)
- 採用時の候補選択だけ composition を張る今の仕組みは、そのまま使える

#### 短所・リスク

- 採用し忘れると、文書にかなのまま残る。従来の IME の「Enter で確定すれば必ず変換済み」
  という感覚とは違う
- 打鍵ごとに PREDICT と CONVSEG/CONVCTX の両方を呼ぶ。非ブロック呼び出しのため
  打鍵は止まらないが、エンジンの応答が遅いと候補バーの更新が遅れる
- 候補バーが常に出ていると、視線の移動や画面の占有が気になる人がいる。
  候補バーを出すかどうかは設定で切り替えられるようにする
- 候補ウィンドウ (candidate_window.cpp) は縦一覧の前提なので、横並びの表示モードが要る
- パスワード欄などでは出さない判定が要る (今の IME オフ運用で足りるかは要確認)

## 推奨 (草案)

方向性は2通りある。他の大規模変更 (連文節変換をやめる案) との組み合わせで選ぶ。

- 短期・小規模: 案A + 案B。どちらもエンジン変更なしで、挙動が予測可能。
  案A はまず Esc の正式化 (未変換ローマ字の救済を揃える) で始め、専用キーの要否は
  常用して判断する。揺れが残るなら案C (C2) を設定オプションとして検討する。
  案D は保留
- 長期・大規模: 案E。ライブ変換・予測サジェスト・変換候補を候補バーにまとめ直す、
  入力 UX 全体の作り直しになる。連文節変換をやめる案と一緒に設計するのが効率が良い。
  採るなら案A〜D は不要になる (案E の中では、採用した結果は変わらないため)

## 他の変更との関係

- docs/archive/single-unit-conversion-notes.md (連文節変換をやめる案) が採用されると、
  ライブ変換の表示単位そのものが変わる。案A・案B は文節に依存しないので影響を受けにくい。
  案C・案D は文節を前提にしているため、そちらの方針が決まってから判断する
- composition 方式では Enter が確定キーなので案A は不要。案B を composition 方式にも
  適用するかは未決
- モードレス入力の英字モード中はライブ変換が効かないため、いずれの案も対象外

## 未決事項

- 案A の確定キーの割当 (Esc の正式化のみか、無変換などの専用キーを足すか)
- 案B の区切り文字の集合 (、。のみか、！？・「」なども含めるか) と既定のオン/オフ
- 案B を composition 方式にも適用するか
- 案C を採る場合の固定条件 (文節数・打鍵数) と、固定した文節の見た目上の区別の要否
- 自動で確定・固定した結果も LEARN の対象にするか (現状は Space での run 終了でも
  ライブ結果を学習しており、ユーザが確認していない結果を学習する点は同じ)
- 案E: 候補バーの並び順 (全体変換・予測・先頭文節の混ぜ方) と候補数
- 案E: 採用キーの割当 (変換キー・Tab・Enter・番号選択の修飾キー)
- 案E: 採用しないまま run が終わったとき (Space・Enter・キャレット移動) の扱い。
  かなのまま残すか、全体変換で採用するかを設定にするか
- 案E: 表示位置 (行の下か上か、run 先頭に固定か) と、ブラウザの入力補完との重なりへの対処
- 案E: 後続語予測 (読みなしの予測) を入れるか。入れるならエンジンの予測モデルと
  プロトコルの追加が要る
- 案E: composition 方式でも候補バーを使うか (composition 方式は Enter で確定する
  前提なので、そのままでは原則と合わない)
