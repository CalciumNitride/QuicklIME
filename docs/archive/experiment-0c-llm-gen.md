# 実験 0c: LLM による候補の生成の計測

LLM による候補の生成 ([roadmap](../roadmap.md)) を採るかどうかと、その方式を決めるための計測の仕様。
並べ替え ([llm-rerank.md](../design/llm-rerank.md)) は N-best の上位 10 件の中でしか順位を直せない。
生成を足すと、その外にある正解にどれだけ届くかを、遅延・副作用と合わせて測る。

## 背景と目的

AJIMEE-Bench (197 件、左文脈あり、前文脈なし) で、Vulkan 版と zenz-v3.2-small を使って今の並べ替えを測った結果は次のとおり。

| 並び | 1位 | 上位3件 | 上位10件 |
|---|---|---|---|
| 並べ替え前 (統計) | 102 (52%) | 135 (69%) | 163 (83%) |
| 並べ替え後 (LLM) | 131 (66%) | 159 (81%) | 163 (83%) |

- 正解が上位 10 件に入らない件が 34 件ある。並べ替えでは直せない
- その多くは辞書にある語の組み合わせで、長い読みの中の 1 か所で語の選び方を誤り、正しい組み合わせが N-best に
  残っていない (「時期皇帝」と「次期皇帝」、「検討をつけた」と「見当をつけた」、「対空機従軍」と「対空機銃群」)

本実験では、次の 2 つの生成の方式を比べ、製品に入れるかと、入れるならどちらの方式にするかの材料を得る。

- 精度: 並べ替えだけのときより 1 位の正解率が上がるか。並べ替えで当たっていた件を壊さないか
- 速さ: 候補バーへ非同期で反映するのに間に合う遅延か
- 副作用: 読みから外れた出力 (読みに無い語・数字や英字の書き換え・止まらない生成) がどれだけ出るか

製品に入れるときは、並べ替えと同じく非同期で候補バーの全体変換の枠に入れる想定で指標を決める。
製品への組み込み (プロトコル・TSF 層・設定) は本実験の対象外で、結果を見てから別の設計書で扱う。

## 決定事項

### 比べる方式

#### A. 自由生成と後処理

zenz に読みから表記を生成させ、出力を後処理で検査する (rakukan の方式。[rakukan-llm-notes.md](../archive/rakukan-llm-notes.md))。

- 貪欲法 (毎トークン argmax) と、beam 幅 3 の beam search の 2 通りを測る。beam search は累積の対数確率の
  高い順に最大 3 件を出す
- 生成は EOS か上限 (読みの文字数 × 2 + 8 トークン。0b と同じ) で止める。上限で止まった出力は捨てる
- 読みはそのまま 1 回で渡す (句読点・数字・英字を含めて)。rakukan のように数字・英字・記号の区間を分けて
  かなの区間だけを生成する処理 (リテラル保護) は本実験では入れず、書き換えの件数を測るだけにする
- 後処理 (rakukan に倣う):
  - ルビの除去: 括弧 (`(` `)` `（` `）`) の中がかなだけなら括弧ごと消す。ただし読み自体にその括弧があれば消さない
  - 長さの上限: 出力の文字数が読みの文字数を超えたら捨てる (表記は読みより長くならない前提)
  - 繰り返しの棄却: 同じ 2 文字以上の並びが 3 回以上続けて現れる出力を捨てる。読み自身に同じ繰り返しがあれば捨てない
- 文脈のエコー対策は入れない。左文脈から読みのひらがなをそのまま写した出力の件数だけを数える
  (出力に左文脈と共通の 4 文字以上のひらがなの並びがあり、それが読みにもある件)

#### C. 統計変換をドラフトにした照合 (Zenzai 方式)

azooKey の Zenzai (AzooKeyKanaKanjiConverter の `zenzai.swift` と `ZenzCandidateEvaluator.swift`、
コミット `04ce2ec`) の手順に倣う。表記の接頭辞の制約を付けた Viterbi で作ったドラフトを LLM で 1 回評価し、
LLM の予測とずれたら制約を更新して、Viterbi からやり直す。

1. 制約は (表記の接頭辞のバイト列, 完全一致か) の組。最初は空の制約
2. ドラフト: 制約を満たす経路のうちコスト最小のものを Viterbi で求める。満たす経路が無ければ打ち切る
   - 最初のドラフトは統計の 1-best (`convert_nbest_rerank` の通常の最良経路) と同じになる
   - 制約が更新されたら、まず最初の N-best の上位 10 件から、制約を満たす最上位の候補を探してドラフトにする
     (Zenzai の retry と同じ。Viterbi と推論を減らすため)。無ければ制約つきの Viterbi を解く
3. 評価: プロンプトの後ろにドラフトのトークンと EOS をつなげ、1 回の decode で全位置の logits を得る。
   ドラフトの各トークンの位置で、argmax のトークンと比べる
   - すべて一致 (EOS の位置で EOS が argmax): 合格。ドラフトを結果にして終わる
   - ある位置で argmax が EOS: その位置までのドラフトの表記を完全一致の制約にする
   - ある位置で argmax が別のトークン: その位置までのドラフトの表記に argmax のトークンの文字列をつないだものを
     接頭辞の制約にする (トークンは文字の途中で切れることがあるので、制約はバイト列で持つ)
4. 新しい制約が前と同じなら打ち切る。評価の回数が上限 (`--limit`、既定 10) に達したら打ち切る
5. 打ち切ったときは、最後に評価したドラフトを結果にする

- 制約つきの Viterbi は `engine/src/convert.rs` に足す。状態を (読みの位置, 制約のバイト列のうち一致した長さ) に
  広げた Viterbi で、ノードの表記が制約のバイト列の続きと食い違う遷移は通さない。一致した長さが制約の長さに
  達した後は、制約の無い Viterbi と同じ。完全一致の制約では、EOS へ着く経路の表記が制約と等しいものだけを通す。
  コスト (連接・語・文節境界のペナルティ) は今の Viterbi と同じ
- 学習・ユーザ辞書を使わないので (計測は空の学習で行う)、Zenzai の「学習の候補を外して再試行する」処理は入れない
- プロンプトの KV キャッシュは 1 回だけ作り、評価のたびにドラフトの部分だけを作り直す
- C の出力は、辞書のラティスの経路でたどれる表記になるので、読みから外れない

#### 採らなかった案

- B. 辞書のラティスに制約した LLM の beam search (ラティスの語の境界とトークンを対応づけ、LLM のスコアだけで
  経路を探す): C と同じく読みから外れないが、ラティスとトークンの対応づけの実装が重い。A と C の結果を見て、
  C の遅延か精度に問題があるときに検討する
- jinen (karukan のモデル) を比べること: ライセンス (CC BY-SA 4.0) とプロンプトの形式が zenz と違う。
  モデルは zenz だけにする

### 製品に入れたときの並びの仮定

指標を「並べ替えと合わせた並び」で測る。製品では、生成した候補を候補バーの全体変換の枠の先頭に入れる想定。

- 合わせた並び: 生成の結果 (A の beam は最大 3 件、A の貪欲法と C は 1 件) を先頭に置き、その後ろに並べ替えの
  結果を続ける。同じ表記は先勝ちで除く
- 並べ替えの結果は example の中で求める。CONVNBEST と同じ `convert_nbest_rerank` の上位 10 件を、製品と
  同じプロンプト・尤度で並べ替える。読みが `RERANK_MIN_CHARS` (9) 文字未満なら並べ替えない。保護の印
  (学習・ユーザ辞書・英字) は、英字を含む候補だけが関わる (空の学習のため)。製品と同じ規則で動かさない
- 生成にも同じ読みの長さのしきい値を当てるかは結果で決める。計測では全件で生成し、読みの長さ別にも数える

### 対象のモデルと環境

製品の設定と同じ組み合わせで測る。

| 組み合わせ | exe の feature | モデル | スレッド |
|---|---|---|---|
| CPU | `llm-bench` | zenz-v3.2-xsmall (Q5_K_M) | 4 |
| Vulkan | `llm-bench-vulkan` | zenz-v3.2-small (Q5_K_M) | - |

- モデルは `scripts\fetch-models.ps1` で取得した `models\` のものを使う
- プロンプトの書式・前処理・tokenizer.ggml.pre の上書きは llm_bench / quicklime-llm と同じ。読みはカタカナにして渡す

### テストセット

- AJIMEE-Bench (`references/AJIMEE-Bench/ajimee_cases.tsv`、197 件): 結果の報告に使う
- llm_cases.tsv (50 件): 短い読みで左文脈が効く件が多い。並べ替えの調整に使ったセットなので、
  報告は参考の値として分けて出す
- どちらも左文脈あり、前文脈 (統計変換の直前文節) なし。学習・ユーザ辞書は空

### 計測項目

方式 (並べ替えだけ・A 貪欲法・A beam・C) ごと、テストセットごと、組み合わせ (CPU・Vulkan) ごとに出す。

精度:

- 方式の単独の結果が正解と一致した件数 (A beam は 1 件目と、3 件のどれか)
- 合わせた並びで正解が 1 位・上位 3 件・上位 10 件に入る件数
- 並べ替えだけと比べた 1 位の得失: 並べ替えで外れていて合わせた並びで当たった件数 (得)、その逆 (失)
- 上位 10 件に正解が無かった件 (AJIMEE-Bench の 34 件) のうち、方式の結果が正解だった件数
- 読みの長さ別 (9 文字未満・9 文字以上) の 1 位の件数

速さ (ウォームアップの後に、件ごとに 1 回):

- 方式ごとの 1 件あたりの時間 (中央値・p95・最大)。並べ替えの時間と、生成または照合の時間を分けて出す
- 読みの長さ別 (9 文字未満・9〜19・20 以上) の中央値・p95
- C の評価の回数の分布 (1・2・3・4〜6・7 以上) と、合格・制約の繰り返しでの打ち切り・上限での打ち切り・
  制約を満たす経路が無いことでの打ち切りの件数

副作用 (A だけ):

- 上限で止まった件数、後処理で捨てた件数 (ルビの除去は件数だけ、長さ・繰り返しで捨てた件数)
- 読みから外れた出力: 完全一致の制約つきの Viterbi で、出力と同じ表記の経路が無い件数と、そのうち正解だった件数
  (辞書に無い語を正しく出した件と、読みと違う語を出した件が混ざる。件ごとの表で目で見て分ける)
- 読みの数字・英字が出力に同じ並びで残っていない件数
- 左文脈のエコーの件数

### 実装の形

- 新しい example `engine/examples/llm_gen_eval.rs`。feature は llm_bench と同じ `llm-bench` / `llm-bench-vulkan` で、
  `required-features = ["llm-bench"]` を付ける (通常のビルド・テストではビルドしない)
- 辞書は nbest_eval の `Converter::load` と同じ規則で読み込み、変換は `#[path]` で取り込んだ src のモジュールを
  プロセス内で呼ぶ。LLM も llama.cpp をプロセス内で使う (エンジン・quicklime-llm を起動しない)
- llama.cpp の扱い (読み込み・プロンプト・尤度の求め方) は llm_bench.rs の `Llm` と同じものを使う。
  llm_bench.rs から共通の部分を別ファイルに出して両方から `#[path]` で取り込むか、llm_gen_eval.rs に写すかは
  実装で決めてよい (llm_bench の出力は変えない)
- 結果は標準出力に Markdown で出す (nbest_eval と同じ書き方)。`--no-cases` で件ごとの表を出さない
- 引数: `--model <gguf> --backend cpu|vulkan [--threads N] --cases <tsv> [--limit N] [--methods rerank,a-greedy,a-beam,c] [--no-cases]`
- 件ごとの表の列: 番号・左文脈・読み・正解・並べ替えの 1 位・A 貪欲法・A beam (3 件)・C の結果・
  C の評価の回数と終わり方・合わせた並びでの順位 (方式ごと)

### 追加の計測: A と C の組み合わせ

A 貪欲法の精度と、C の読みから外れない性質を合わせる方式を、Vulkan + small だけで測る
(CPU + xsmall では A・C とも得に対して失が多く、生成は Vulkan のときだけに使う想定のため)。

- 方式 `a+c`: A 貪欲法の出力を使う。後処理で捨てたときと、読みから外れたとき (完全一致の制約つきの Viterbi で
  同じ表記の経路が無い) は、C の結果に代える
- 並べ替えは終わりの項を `</s>` にした今の製品の並べ替え (AJIMEE-Bench の 1 位 141 件) を使う。A 貪欲法・A beam・C も
  同じ条件で測り直す
- 測るもの: 合わせた並びの 1 位・上位 3 件・上位 10 件、並べ替えだけと比べた得失、上位 10 件に正解が無かった件のうち
  拾えた件数、C に代えた件数とそのうち C の結果が正解だった件数・A の出力が正解だった件数 (数の書き方など、読みから
  外れても正しい件を失う分)、時間 (C に代えた件は A と C の合計。中央値・p95・最大、読みの長さ別)
- 引数 `--methods` に `a+c` を足す。C を代えるときだけ実行するのではなく、計測では全件で A と C を両方求め、
  `a+c` の時間は代えた件だけ C の時間を足して出す

## 実装手順

1. 制約つきの Viterbi と単体テスト。`cargo test` が通り、空の制約で今の Viterbi と同じ経路になることを確かめる
2. llm_gen_eval: 並べ替えだけを実装し、AJIMEE-Bench の 1 位・上位 3 件が nbest_eval `--llm vulkan` の結果
   (131 / 159) とほぼ同じになることを確かめる。差があればその件と理由を結果に書く
3. A (貪欲法・beam・後処理・副作用の数え上げ)
4. C
5. 計測し、結果を experiment-0c-llm-gen-results.md に書く (0b の結果の書き方に倣い、事実だけを書き、採否の判断はしない)
6. 追加の計測 (`a+c`)。結果は experiment-0c-llm-gen-results.md に節を足して書く

## 検証方法

### 単体テスト (制約つきの Viterbi)

- 空の制約では今の Viterbi の最良経路と同じ
- 接頭辞の制約 (例: 「きのうはあめがふった」に「昨日は飴」) で、表記がその接頭辞で始まる経路のうち最小コストのものになる
- 文字の途中で切れたバイト列の制約 (漢字 1 文字の UTF-8 の先頭 1〜2 バイト) でも、その文字で始まる経路を返す
- 完全一致の制約で、表記が等しい経路を返す。等しい経路が無ければ None
- 満たす経路が無い接頭辞の制約で None

### 計測の確かめ

- 手順 2 の並べ替えだけの数値が nbest_eval と合う
- 件ごとの表で、C の打ち切りの件と A の読みから外れた件を数件ずつ目で見て、数え方が仕様どおりか確かめる
- CPU と Vulkan の両方で最後まで走る

### 判断の目安

結果の記録では判断をせず、製品に入れるかを決めるときの目安として次を使う。

- 精度: AJIMEE-Bench の合わせた並びの 1 位が、並べ替えだけ (66%) より明らかに上がり、llm_cases.tsv の 1 位が下がらない
- 速さ: 9 文字以上の読みで、Vulkan の p95 が 300 ms 以下、CPU の p95 が 1000 ms (TSF 層の問い合わせの打ち切り
  `LLM_POLL_LIMIT_MS`) 以下
- 副作用 (A): 読みから外れた出力のうち、正解でないものが 1 位に来る件が、得の件数より十分少ない

## 未決事項

- 生成した候補を全体変換の枠のどこに入れるか (先頭か、並べ替えの 1 位の次か)。結果の得失で決める
