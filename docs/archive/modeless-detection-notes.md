# モードレス入力の英語判定 強化案 (草案)

作成日: 2026-10-07

本メモは、モードレス入力 (docs/design/modeless.md) の自動英字判定を強化するための
アイデアの草案。参考として Meltype (https://github.com/yksr-melt/Meltype、
commit 45711a0 時点) の判定方式を調査した。**方針は未決定で、コードは未着手**。
採用する項目が決まったら、docs/design/modeless.md の改訂または新しい設計ドキュメントに
落とし込む。

## 現状の QuicklIME の判定

docs/design/modeless.md と tsf/src/romaji.cpp の `RomajiComposer` による。

- 英字と判定するルールは3つ
  1. ローマ字として成立しない英小文字が素通しされた (`apple` の `pl`、`th`、`str`)
  2. 「っ」の直後に小書き母音が来た (`hello` の「へっ」+「ぉ」)
  3. 確定時に、未変換のローマ字として n 以外の子音が1文字残っている (`want` の「わんt」)
- ローマ字として成立する英単語 (`pen` `name` `sake`) は判定しない (日本語を優先する)
- 判定が成立すると `SwitchToAscii()` が run 全体の打鍵列 `Raw()` から英字に作り直す。
  一度英字になった run は日本語に戻らない
- 文脈 (直前に確定した文字列)・辞書・学習は判定に使っていない

既知の限界:

- `this is a pen.` の `pen` のように、英文の途中にあるローマ字として読める語は日本語になる
- コードを読む限り、`kyouhagithub` のように日本語に続けて英単語を打つと、`th` の時点で
  run 全体が `kyouhagith` になると考えられる (実機では未確認)

## Meltype の判定方式 (調査結果)

Meltype は Windows の IME を OFF にしたまま、キーボードフックと自前の変換ボックスで
入力を受け持つ常駐アプリ。かな漢字変換は Mozc / Microsoft IME (IFELanguage) を外から呼び出し、
Meltype 自身の独自部分は日本語と英語の自動判定と、変換ボックスの UX にある。

判定は機械学習ではなく、ルール・辞書・スコアの組み合わせで行っている。

### 打ち始めの1語の判定 (ScoreEngine)

IME 自動切替モード用。保留した最大6文字を各判定器に通し、日本語点と英語点を合計する。

| 判定器 | 内容 |
|---|---|
| ローマ字解析 | 成立しなければ英語に確定。日本語特有の綴り (`kya` などの拗音 +3、`tsu` +3、長音 +1、促音 +1) |
| 日本語辞書 | ローマ字の見出し語と前方一致 (完全一致 +5、前方一致 +3〜4)。見出し語から `si/shi`、`tu/tsu`、`n/nn` などの綴りの揺れを展開して登録する |
| 英語辞書 | 完全一致で英語 +4、前方一致で英語 +3 |
| 学習・打ち間違い | ユーザーの修正履歴など |

日本語と判定する条件は `日本語点 >= 4` かつ `日本語点 - 英語点 >= 4`。
`as` (ashita の打ち始め) のように日本語の語の途中になり得る間は判定を保留する。

### 文の中での英語区間の切り出し (CompositionDetector)

メインモード用。既定は日本語とし、英語と言える根拠がある区間だけを英字のまま残す。
区間の区切り目はかな1音の境目だけで、先頭から「この位置から始まる最長の英語区間」を探す
(`kyouhagoogledekensaku` → `kyouha` | `google` | `dekensaku`)。

英語の根拠:

- ローマ字として読めない文字を含む英単語 (`zoom`)、子音で終わる英単語 (`git`、`about`)
- ローマ字では読めても日本語にならない英単語のリスト (`feature`、`remote` など十数語)
- c 行の綴り (`camera`)、ローマ字読みで「ぢ」「づ」になる綴り (`radio`、`studio`)。
  日本語を打つときは k や z を使うため。5文字以上の英単語に限る
- 固有名詞辞書 (`amazon`、`netflix`)。偶然の一致を避けるため4〜5文字以上
- Shift で打った大文字始まりの語
- Windows のスペルチェッカー API。`kore` のようなローマ字の語まで通すため、
  ローマ字として読めない語か、文脈で英語と分かるときだけ使う
- 短縮形 (`don't`)、ハイフン語 (`e-mail`)、`@` メンション、`_` を含む語、ドメイン名

英語とも日本語とも読める語 (`sushi`、`make`、`no`) は前後の文脈で決める:

- 前が英語なら +1、日本語なら -1、英文の続き (`I want ` の後ろ) なら +2。後ろも同様に数える
- キャレット前後の確定済みテキストは UI Automation で取得する
- 助詞と同じ形の2文字の語 (`no` `to` `ga`) は、前後の両方が英語のときだけ英語とする

日本語として扱う個別の例外も多い (`push` + `shite` → 「pushして」、`grok` + `ga` → 「grokが」)。

### 学習

変換ボックスで F10 (英字) / F6 (ひらがな) で直して確定した語を覚え、次から優先する。
ただし `go` のような短くローマ字として読める語は、日本語の直後 (`nihon|go`) では使わない。

| ファイル | 規模 | 出典 |

## 応用案

### A. 直前の確定文字列を文脈に使う

TSF 層はすでに `contextSurface_` (直前に確定した文字列) を持っている。これが英語で
終わっていれば、ローマ字として読める短い語も英語寄りにする。

- 効果: `this is a pen.` の `pen` を拾える。英文を続けて打つ場面で効く
- コスト: 低い。辞書は不要で、romaji.cpp の判定に文脈フラグを渡すだけ
- リスク: 英単語の直後に日本語を打つ場面 (`GitHub` + `no` → 「の」) で誤判定する。
  2文字の助詞と同じ形の語は除外する、などの例外が要る
- 検討事項: direct 方式で、文脈をどこまで信用できるか (アプリによっては取得できない)

### B. 英字にする範囲を run の途中からに限定する (区間分割)

判定が成立したとき、run 全体ではなく、英単語の始まり以降だけを英字に作り直す。

- 効果: `kyouhagithub` → 「きょうは」+ `github`。モードレス入力の体験として最も効く
- コスト: 中〜高。英単語の始まりを決めるには英単語の知識 (C) が要る。
  辞書なしのヒューリスティクス (直前のかな1〜2音だけを英字側に寄せる) は誤りが多いと見込まれる
- 検討事項:
  - run を分割するのか、run 内に日英の区間を持たせるのか (RomajiComposer のデータ構造に影響する)
  - 英語区間の後に日本語が続く場合 (`github` + `de`) に日本語へ戻れるようにするか。
    現状の「一度英字になったら戻らない」仕様の見直しになる
  - direct 方式では文書上の書き換えが発生する (チラつき・Undo)

### C. 英単語の知識を持つ

docs/design/modeless.md では辞書配布とメモリのコストを理由に見送った案。次のいずれかで再検討する。

| 方式 | 長所 | 短所 |
|---|---|---|
| Windows スペルチェッカー API (`ISpellChecker`) | 辞書の配布が不要 | ローマ字の語 (`kore`) まで通す。COM 呼び出しの遅延 |
| SCOWL から作った単語リストの同梱 | 環境に依存しない、挙動が安定する | 配布サイズ (数万語で数百 KB 程度)、著作権表示 |
| 小さな手作りリスト | 軽い | 網羅性が低い |

- 呼び出し場所は TSF 層 (全アプリのプロセスにロードされる DLL) よりも、エンジン (Rust) 側が
  安全と考えられる。ただし打鍵ごとのパイプ往復の遅延を評価する必要がある
- Meltype の「ローマ字として読めても日本語にならない語」のリスト (`feature`、`remote`) は、
  小さくて効果が分かりやすいので、C の中でも先に入れやすい

### D. 日本語側の根拠にエンジンの辞書を使う

Meltype は日本語辞書を自前で持つが、QuicklIME にはかな漢字変換エンジンの辞書がある。
「そのかな列が日本語の語か (前方一致か)」をエンジンに問い合わせれば、強い日本語の根拠になる。

- 効果: ローマ字として読める英単語 (`make`、`name`) を、日本語の語にならないことを根拠に英語にできる
- コスト: 中。プロトコルの追加と、打鍵ごとの問い合わせの遅延対策
- 検討事項: 既存のライブ変換・予測の問い合わせに相乗りできるか (docs/protocol.md)

### E. 綴りのヒューリスティクス

辞書なしで足せる軽いルール。

- c 行の綴り (`ca` `cu` `co`)、ローマ字読みで「ぢ」「づ」になる綴りは英語寄り。
  ただし短い語や、c 行で日本語を打つ利用者への影響があるため、5文字以上などの条件を付ける
- 現行のローマ字テーブル (AZIK など、設定 romaji) によって成立する綴りが変わる点に注意する

### F. 修正の学習

F10 などで英字に直して確定した語を覚え、次から英語と判定する。逆に、英字と判定された語を
かなに直したら、次から日本語とする。

- コスト: 中。学習データの保存先 (エンジンの learn.rs に載せるか) の設計が要る
- Meltype と同様に、短くてローマ字として読める語は、日本語の直後では学習結果を使わない

## 段階案

1. A (文脈) と E (綴り) のうち安全なもの。辞書なしで、現行のデータ構造のまま入れられる
2. C の小さなリスト (ローマ字として読めても日本語にならない語)
3. B (区間分割) と C (本格的な英単語の知識)。データ構造の変更を伴うため、
   他の大幅な変更の方針が固まってから設計する
4. D と F

## 共通の注意点

- Meltype は GPL-3.0 のため、コードやルール表をそのまま移植しない。考え方だけを参考にし、
  辞書は SCOWL など元のデータから自分で作る
- Meltype は自前の変換ボックスで、確定までは何度でも表示を作り直せる。QuicklIME の direct 方式は
  文書に直接書き込むため、判定を覆すたびに文書を書き換えることになる。積極的に判定するほど、
  チラつきと Undo の問題 (docs/design/modeless.md の未決事項) が重くなる
- 判定精度の評価方法が必要になる。Meltype は品質テストでカテゴリーごとの正解率を測っている。
  QuicklIME でも、打鍵列と期待する結果 (日本語 / 英語の区間) の対を集めたテストセットを作るとよい
